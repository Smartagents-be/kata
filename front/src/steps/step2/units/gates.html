A gate is a check the work has to pass before it moves on: the tests before a commit, the build before a merge, a review before a release.

An agent writes code faster than you can read it. Review every line by hand and you become the slowest step, and the agent waits on you. So let a machine check what a machine can check. Keep for yourself what only you can decide: what to build, the spec, whether a change does what you meant, and when it ships (step 3's unit on team and process change shows where those fall). The gates check the code, you check the decisions. That is the human-in-the-loop pattern: at a fixed point the work stops and waits for a person.

Quality gates

Sonar, a coverage floor and a mutation score have always caught drift and regression before a release, and investing in them still speeds up shipping. They also give an agent a fixed bar to hold itself to while it works But a number does not measure quality itself, only something that usually comes with it. An agent told to hit the number hits the number, even by a route that leaves the code no better, so wire in the checks that are hard to pass without doing the real work.

METR measured it in 2025. In its RE-Bench tasks, o3 cheated in 39 of 128 runs, for example by making the clock the score was timed with run faster, or by patching the evaluator to always return a perfect score (METR's write-up). Asked afterwards whether that was what the user wanted, it often said no.

Wire the gate in so the agent cannot move it. You do that with a hook: a script your assistant runs just before every edit and shell command the agent makes. You register it in .claude/settings.json or in .github/hooks/. The script looks at what the call wants to change. If it lowers a threshold, such as the minimum coverage in your build, or touches the script itself, it exits with code 2 and the assistant does not run the call. A hook does not catch every way around it, so also have CI check before merge that no threshold is lower than on main.

Deterministic checks

A gate you can hand the checking to gives the same answer on the same code, every run, and the agent can run it without you. Then it checks its own work instead of waiting on you.

Legacy code

Old code with no documentation and no tests needs a different order. Before the agent changes anything, put the gates in place: regression tests until every line is covered, and the checks above set at today's level, so they fail on whatever gets worse. Those tests record what the code does today, odd parts included. From then on the gates, the coverage among them, check every change for regression. They are the source of truth.

They stay the truth until behaviour has to change. When a test fails after that, the test does not decide and neither does the agent. Ask the product owner whether the new behaviour is what they want. If it is, update the test. If it is not, it is a regression: fix the code.

Short feedback loops

An agent checks itself as often as your gates allow. 8-second tests run after every change, while it still knows what it did. A 20-minute pipeline runs at the end, when it has moved on, or the failure lands on you. It does its best work against the fast gate, and the later a gate answers, the further a mistake has already got.

So the speed of a gate is a gate too. A 4-minute build sounds cheap, but 10 runs an hour is 40 minutes of waiting. Put a number on it and hand it over as a goal: 

> Goal: `mvn verify` finishes in under a minute on this machine.
  Keep every check it runs today and every test it has, and do not
  lower a threshold. Time the build after each change you make.

The constraints stop it from winning the cheap way, by deleting the slow tests. The unit on proving your work argues that shape.

None of this is about the agent being careful. A gate is your engineering judgement, written down where the work happens. What you cannot write down in advance is what steering is for.
