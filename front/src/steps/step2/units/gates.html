A gate is where the work stops until something says yes. Take the typing away and the queue at the slowest desk does not disappear: it moves to the asking, the reading and, in the end, the deciding.

From idea to production a person still decides 4 times: the intent, the spec, the change and the release (step 3's unit on team and process change draws where). Everything in between is machine work, and it only stays that way if a machine checks it too. Nobody reviews that volume by hand. The gates take the volume, you judge the decisions.

Quality gates

Sonar, a coverage floor and a mutation score have always caught drift and regression before a release, and investing in them still speeds up shipping. They also give an agent a fixed bar to hold itself to while it works But an agent aims for the proxy, not what is behind it, so wire in the gate that is expensive to fake.

Wire the gate in so the agent cannot move it. A hook that runs before every edit and shell command can refuse anything that touches the thresholds or the hook itself: exit code 2 blocks the call in Claude Code and Copilot alike. It is a fence, not a proof, so keep the build as a required check before merge too.

Deterministic checks

A gate worth handing the volume to gives the same answer on the same code, every run, and the agent can run it without you. That is what makes it a loop rather than a queue. Review is for the decisions, and those stay with you.

  • Unit tests check the rules inside 1 module, in seconds.
  • Integration tests run an adapter against the real database: a Postgres in Testcontainers, not a mock.
  • Contract tests keep a screen and its endpoint, or 2 services, in agreement without starting both. Pact records what the consumer expects, and the provider replays it against its own code.
  • Architecture tests fail the build when 1 module reaches into the internals of another. ArchUnit writes that rule as an ordinary test.
  • Coverage and mutation score are 2 numbers about the tests themselves, from JaCoCo and PIT.
  • Static analysis finds known bug patterns and code smells: SpotBugs, PMD, Sonar.
  • Cyclomatic complexity caps the number of independent paths through 1 method. McCabe's limit of 10 keeps a method small enough to read and to test.
  • Vulnerability scans check every dependency against known CVEs: OWASP Dependency-Check, Trivy, Dependabot. Its answer moves without your code moving, because a new CVE turns yesterday's green build red, so it runs on every build.
  • Secret scanning stops a key before it leaves your machine: gitleaks as a pre-commit hook, or push protection on GitHub.

Sonar answers in CI. Run the same kind of rules inside mvn verify with SpotBugs or PMD, and the agent hears them while it still knows what it changed.

Legacy code

Old code with no documentation and no tests needs a different order. Before the agent changes anything, put the gates in place: regression tests until every line is covered, and the checks above set at today's level, so they fail on whatever gets worse. Those tests record what the code does today, odd parts included. From then on the gates, the coverage among them, check every change for regression. They are the source of truth.

They stay the truth until behaviour has to change. When a test fails after that, the test does not decide and neither does the agent. Ask the product owner whether the new behaviour is what they want. If it is, update the test. If it is not, it is a regression: fix the code.

Blast radius

An agent that can run commands can run the wrong one: drop a migration it thinks is stale, rewrite 40 files for 1 line, push the lot. How far that gets before a gate stops it is the blast radius.

Give the agent its own branch, and let protected branches, required checks and review decide what ships. A worktree keeps the files apart, but a command can still reach another checkout or an external service, so limit file, credential and network access separately .

Short feedback loops

An agent checks itself as often as your gates allow. 8-second tests run after every change, while it still knows what it did. A 20-minute pipeline runs at the end, when it has moved on, or the failure lands on you. It does its best work against the fast gate.

So the speed of a gate is a gate too. A 4-minute build sounds cheap, but 10 runs an hour is 40 minutes of waiting. Put a number on it and hand it over as a goal: 

> Goal: `mvn verify` finishes in under a minute on this machine.
  Keep every check it runs today and every test it has, and do not
  lower a threshold. Time the build after each change you make.

The constraints stop it from winning the cheap way, by deleting the slow tests. The unit on long runs argues that shape.

None of this is about the agent being careful. A gate is your engineering judgement, written down where the work happens. What you cannot write down in advance is what steering is for.
