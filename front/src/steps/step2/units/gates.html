A gate is where the work stops until something says yes. Take the typing away and the queue at the slowest desk does not disappear: it moves to the asking, the reading and, in the end, the deciding.

The third row is 1 run with no handoffs, and a person still decides 4 times: the intent, the spec, the change and the release. Everything in between is machine work, and it only stays that way if a machine checks it too. Nobody reviews that volume by hand. The gates take the volume, you judge the decisions.

Quality gates

Sonar, a coverage floor and a mutation score have always caught drift and regression before a release, and investing in them still speeds up shipping. They also give an agent a fixed bar to hold itself to while it works But an agent aims for the proxy, not what is behind it, so wire in the gate that is expensive to fake.

Wire the gate in so the agent cannot move it. A hook that runs before every edit and shell command can refuse anything that touches the thresholds or the hook itself: exit code 2 blocks the call in Claude Code and Copilot alike. It is a fence, not a proof, so keep the build as a required check before merge too.

Old code with no documentation and no tests needs a different order. Before anything changes, have the agent write regression tests until every line is covered. Those tests become the source of truth: they record what the code does today, odd parts included, and from then on they catch every regression an agent introduces. Mix kinds of tests, not just unit tests, and let mutation testing check the tests themselves.

They stay the truth until a change is actually needed. Then the tests do not decide what the new behaviour should be. The stakeholders do. Confirm the change with them first, then update the tests, and only then the code.

Blast radius

An agent that can run commands can run the wrong one: drop a migration it thinks is stale, rewrite 40 files for 1 line, push the lot. How far that gets before a gate stops it is the blast radius.

Give the agent its own branch, and let protected branches, required checks and review decide what ships. A worktree keeps the files apart, but a command can still reach another checkout or an external service, so limit file, credential and network access separately .

Fast enough to answer

An agent checks itself as often as your gates allow. 8-second tests run after every change, while it still knows what it did. A 20-minute pipeline runs at the end, when it has moved on, or the failure lands on you. It does its best work against the fast gate.

So the speed of a gate is a gate too. A 4-minute build sounds cheap, but 10 runs an hour is 40 minutes of waiting. Put a number on it and hand it over as a goal: 

> Goal: `mvn verify` finishes in under a minute on this machine.
  Keep every check it runs today and every test it has, and do not
  lower a threshold. Time the build after each change you make.

The constraints stop it from winning the cheap way, by deleting the slow tests. The unit on long-running goals and cost argues that shape.

None of this is about the agent being careful. A gate is your engineering judgement, written down where the work happens. What you cannot write down in advance is what steering is for.
