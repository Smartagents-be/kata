A gate is a place where the work stops until something answers yes. Take the typing away and the queue in front of the slowest desk does not disappear. It moves. First to what you asked for and to whoever reads what came back, and in the end to the moment someone decides.

The third row is one run with no handoffs, and a person still decides four times: the intent, the spec, the change and the release. Everything between those four is machine work, and it only stays that way if a machine checks it too. Nobody reviews the volume an agent produces by hand. The gates take the volume. You judge the decisions.

Quality gates

Static analysis in Sonar, a line coverage floor, a mutation score: that is how software has always been given a quality label, and how drift and regression were caught before a release. The same gates go around an agent's work, and investing in them is still investing in how fast you ship. They also give it something fixed to hold itself to while it works, an invariant Each of them is a proxy, though, and an agent will satisfy a proxy rather than the thing behind it. The gate worth wiring in is the one that is expensive to fake.

Wire that into the run rather than into your memory. A hook fires once the agent says it is finished, which is the one moment a hook can afford to be slow. mvn verify runs whatever analysis your build has wired in, and a number under the floor comes back as a failure it has to answer for. The same rule written into CLAUDE.md is a request. This one runs whether the agent remembers it or not.

Blast radius

An agent that can run commands can run the wrong one. It drops a migration it decided was stale, rewrites forty files to fix one line, and pushes the lot. How far that gets before something stops it is the blast radius. A gate is where it stops.

So put gates between the agent and whatever you cannot take back. It works on its own branch, in its own worktree, and nothing reaches main without the build and your review. Inside that boundary it can try things, break them and throw them away At worst, a bad run costs you a branch. Not a release.

Fast enough to answer

An agent checks itself as often as your gates let it. Tests that answer in eight seconds get run after every change, and a failure lands while the agent still knows what it just did. A pipeline that takes twenty minutes gets run once, at the end, and what fails comes back to a context that has moved on. Or to you. The gate that answers inside the loop is the one an agent does its best work against.

That makes the speed of a gate a gate of its own. Four minutes a build sounds cheap until you count the loops: ten of them in an hour and the agent spends forty minutes waiting on an answer. So put a number on it, and hand the number over as a goal: 

> Goal: `mvn verify` finishes in under a minute on this machine.
  Keep every check it runs today and every test it has, and do not
  lower a threshold. Time the build after each change you make.

The constraints are what stop it winning the cheap way, because deleting the slow tests is faster too. The unit on the cost of the context window is where that shape is argued.

None of that is about the agent being careful. A gate is your side of the line from the unit on craft, written down where the work happens. What is left is the part you cannot write down in advance, which is what steering is about.
