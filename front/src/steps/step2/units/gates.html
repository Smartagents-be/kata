A gate is a place where the work stops until something answers yes. Take the typing away and the queue in front of the slowest desk does not disappear. It moves. First to what you asked for and to whoever reads what came back, and in the end to the moment someone decides.

The third row is 1 run with no handoffs, and a person still decides 4 times: the intent, the spec, the change and the release. Everything between those 4 is machine work, and it only stays that way if a machine checks it too. Nobody reviews the volume an agent produces by hand. The gates take the volume. You judge the decisions.

Quality gates

Static analysis in Sonar, a line coverage floor, a mutation score: that is how software has always been given a quality label, and how drift and regression were caught before a release. The same gates go around an agent's work, and investing in them is still investing in how fast you ship. They also give it something fixed to hold itself to while it works, an invariant Each of them is a proxy, though, and an agent will satisfy a proxy rather than the thing behind it. The gate worth wiring in is the one that is expensive to fake.

Wire the check into the run. In Claude Code, a Stop hook can run mvn verify and report a failing check back to the agent. The wrapper must use the hook’s blocking response, such as exit code 2 with feedback on stderr; an ordinary build exit code 1 does not block stopping. Guard repeated continuations, and keep the build as a required delivery check too.

Blast radius

An agent that can run commands can run the wrong one. It drops a migration it decided was stale, rewrites 40 files to fix 1 line, and pushes the lot. How far that gets before something stops it is the blast radius. A gate is where it stops.

Give the agent a branch and worktree, then enforce delivery through protected branches, required checks and review. Restrict filesystem access, credentials and network access separately. A worktree alone cannot prevent a command from affecting another checkout or an external service .

Fast enough to answer

An agent checks itself as often as your gates let it. Tests that answer in 8 seconds get run after every change, and a failure lands while the agent still knows what it just did. A pipeline that takes 20 minutes gets run 1 time, at the end, and what fails comes back to a context that has moved on. Or to you. The gate that answers inside the loop is the one an agent does its best work against.

That makes the speed of a gate a gate of its own. 4 minutes a build sounds cheap until you count the loops: 10 of them in an hour and the agent spends 40 minutes waiting on an answer. So put a number on it, and hand the number over as a goal: 

> Goal: `mvn verify` finishes in under a minute on this machine.
  Keep every check it runs today and every test it has, and do not
  lower a threshold. Time the build after each change you make.

The constraints are what stop it winning the cheap way, because deleting the slow tests is faster too. The unit on long-running goals and cost is where that shape is argued.

None of that is about the agent being careful. A gate is your side of the line from the unit on craft, written down where the work happens. What is left is the part you cannot write down in advance, which is what steering is about.
