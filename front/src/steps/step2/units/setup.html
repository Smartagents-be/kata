Skills

A skill is a reusable procedure in .claude/skills/, with its instructions in SKILL.md. Its description makes it available for matching tasks; the body loads when used. That differs from standing instructions read at session startup.

A skill is a reusable procedure in .github/skills/, with its instructions in SKILL.md. Copilot reads .claude/skills/ as well. Its description makes it available for matching tasks; the body loads when used. That differs from standing instructions read at session startup.

Take a job that comes back, adding an endpoint to a step's service: 

---
name: add-endpoint
description: >-
  Add a REST endpoint to a step's Spring project the way the existing ones are built:
  a controller under web/, a record for the response body, and the /api
  prefix the Vite proxy expects. Use whenever you add a route, a response shape, or a
  controller to exercises/stepN/java.
---

The name matches the folder, and it is what you type after the slash. The description says what the skill does and when to reach for it, in the words somebody would actually type ("add a route", "add a controller"), because that is what the match is made against. A description reading "helps with the backend" never fires.

Keep them small. A skill may point at another rather than repeat it: a skill that ends by asking for a commit names commit-message instead of restating the rules for one. Detail that will not fit goes in a references/ folder beside the body, read only when it is wanted.

Be sparing with them. You pay for a description on every turn whether or not it fires, so 30 skills are a table of contents the agent reads before every answer. 2 that sound alike are worse than 1: if either could match, neither reliably does. Write one when you are tired of correcting the same thing, not in anticipation of correcting it.

Hooks

A hook is a script your harness runs at a fixed moment, whether or not anybody remembered to ask for it. You declare it in settings.json against an event: before a tool runs, after a file is written, when the session ends.

A hook is a script your harness runs at a fixed moment, whether or not anybody remembered to ask for it. You declare it in a JSON file in .github/hooks/ against an event: before a tool runs, after it ran, when you send a prompt. Copilot CLI only runs them in a folder you trusted.

      {
        "matcher": "Write|Edit",
        "hooks": [

        ]
      }
    ]
  }
}
{
  "version": 1,
  "hooks": {
    "postToolUse": [

    ]
  }
}

So reach for one when a step must happen every time and you would rather not find out that it did not. Then keep it fast and keep it narrow. That script runs on every write, and a broken one hands the agent an error it did not cause. The agent works around that instead of writing your code. When the thing that keeps coming back is a correction rather than a command, the patterns unit is where it goes.

Skills, hooks, agents and MCP servers also come bundled as plugins, installed in 1 step: /plugin in Claude Code, copilot plugin in Copilot CLI. For Java, install a language server as well. The agent then finds code by symbol and sees compiler errors without running the build (the jdtls-lsp plugin in Claude Code, .github/lsp.json in Copilot CLI).

Permissions and sandboxing

A starting directory focuses discovery; a worktree separates checkouts. Neither restricts capability. Claude Code permissions control tool actions: allow and deny rules under permissions in .claude/settings.json for the team, or in .claude/settings.local.json for you alone. Its sandbox restricts filesystem and network access for sandboxed commands. By default, sandboxed commands can still read most of your machine, ~/.ssh included, and file tools, hooks and local MCP servers run outside the sandbox.
