An agent starts every session knowing nothing about how you work here. Project setup is the work of writing that down once, in the repository, so it arrives before your first message instead of after your third correction.

Two places carry it, and they sit next to each other at the root of the project.

This repo has the CLAUDE.md and the two skills today. The settings.json, the hooks and the references/ folder are what you add when you need them, so read the drawing as the shape rather than an inventory.

CLAUDE.md

Everything in CLAUDE.md is read at the start of the session and stays in the window for the whole of it. That is what makes it useful: the agent knows Java is on 25, that assertions use AssertJ, and that steps may import from shared but never the other way round, before you have said a word.

It is also what makes it expensive. Those tokens are re-sent on every single turn, so a file that has grown to a thousand lines is a bill you pay per message, all session. Worse, the instruction that actually mattered is now one line among hundreds, competing for attention with the rest.

So keep it lean. A line earns its place when it changes what the agent writes and cannot be read off the code in a moment. Conventions, invariants, the command that runs the tests: yes. A paragraph explaining what a controller is, or a list of every file in the project: no. The file is a briefing, not documentation.

Skills

A skill is a folder under .claude/skills/ with a SKILL.md in it, holding a procedure you want followed the same way every time. This kata has two: lesson-writing, which is why none of this text contains an em-dash, and quiz-writing.

The interesting part is when they load. Only the frontmatter of every skill is in the window at the start. The body is read when the task matches, and costs nothing until then. That is the difference between a skill and CLAUDE.md: one is always-on and paid for constantly, the other is picked up on demand.

Which puts the weight on the frontmatter. It is two fields, and they are not decoration: 

---
name: lesson-writing
description: Write or revise kata lesson text (front/src/steps/*/units/*.html) so it
  reads like a person explaining something out loud. Use whenever you add a step or
  unit, rewrite lesson content, translate a lesson, or edit any student-facing prose
  in this repo. Bans em-dashes.
---

The name matches the folder. The description has to say two things: what the skill does, and when to reach for it. Write the second half with the words somebody would actually type ("translate a lesson", "add a quiz"), because that is what the match is made against. A description reading "helps with content" never fires.

Keep the body short enough to read in one go and push the detail into references/ next to it. A skill nobody can finish reading has the same problem as a bloated CLAUDE.md, just later in the session.

A quick check on any skill you write: cover the body and read only the description. If you cannot tell from it alone whether the skill applies to the task in front of you, neither can the agent, because that is all it has at that moment.

Hooks are the third piece and the strictest one. They are declared in settings.json and run a script at a fixed moment, whether or not anybody remembered to ask. The unit on repeating patterns comes back to when that is the right answer.
