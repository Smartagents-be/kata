A session needs the relevant instructions about your project. Put durable conventions and reusable procedures in the repository so you do not have to explain them each time .

A few specialised files do that, and each one sits where it applies.

Keep each one lean. Every line adds entropy and costs tokens on every turn A bloated file buries the instructions that matter. For each line, ask: would the agent make mistakes without it? If not, cut it. /init writes a first draft in Claude Code. In Copilot it writes .github/copilot-instructions.md instead, so ask for an AGENTS.md in a prompt. Hold every line of it to that test.

A nested CLAUDE.md follows the folders, and some conventions cut across them: how a controller is built holds in every module that has one. Those go in .claude/rules/ 4, 1 file per topic. Subfolders such as frontend/ and backend/ keep them in order, but only a paths line decides where a rule applies. With that line, the rule joins the context once the agent reads or writes a matching file. Without it, the rule loads at every session start, like the root file. An @docs/api.md line in a CLAUDE.md pulls that file in at the start, which shortens the CLAUDE.md but not the context.

Your own instructions

There is one more, and it is not in the repository. ~/.claude/CLAUDE.md in your home directory is read in every project you open on this machine. It holds how you work rather than what the project is: the language you want to be answered in, the tools you always reach for, the thing you are tired of asking for 2 times a day. Skills

A skill is a reusable procedure in .claude/skills/, with its instructions in SKILL.md. Its description makes it available for matching tasks; the body loads when used. That differs from standing instructions read at session startup. A file in .claude/commands/ is the older form of the same thing: commands/diagnosing-bugs.md and skills/diagnosing-bugs/SKILL.md both give you /diagnosing-bugs. Old ones keep working. Write new ones as a skill, which can hold more files than 1.

A skill is a reusable procedure in .github/skills/, with its instructions in SKILL.md. Copilot reads .claude/skills/ as well. Its description makes it available for matching tasks; the body loads when used. That differs from standing instructions read at session startup. A prompt file in .github/prompts/ comes close: diagnosing-bugs.prompt.md runs in IntelliJ when you type /diagnosing-bugs. Unlike a skill, it never runs unless you type its name.

Take a skill many people use, diagnosing-bugs from Matt Pocock's collection: 

---
name: diagnosing-bugs
description: >-
  Diagnosis loop for hard bugs and performance regressions. Use when the user
  says "diagnose"/"debug this", or reports something broken/throwing/failing/slow.
---

The name is how you call the skill: /diagnosing-bugs. The description is the text the agent matches against when it looks for a skill, so it decides whether your skill is ever used. Write it in the words somebody would actually type. A description reading "helps with the backend" never fires.

Keep them small. A skill may point at what already exists rather than repeat it: code-review reviews against the coding standards the repository already documents, such as CONTRIBUTING.md, instead of restating them. Detail that will not fit goes in a file beside the body, read only when it is wanted: diagnosing-bugs keeps a script in scripts/.

Be sparing with them. You pay for a description on every turn whether or not it fires, so 30 skills are a table of contents the agent reads before every answer. A skill only you start gets disable-model-invocation: true, and its description stays out of the context until you call it with a slash. 2 that sound alike are worse than 1: if either could match, neither reliably does. Write one when you are tired of correcting the same thing, not in anticipation of correcting it.

Hooks

A hook is a script your harness runs at a fixed moment, whether or not anybody remembered to ask for it. You declare it in settings.json against an event: before a tool runs, after a file is written, when the session ends.

A hook is a script your harness runs at a fixed moment, whether or not anybody remembered to ask for it. You declare it in a JSON file in .github/hooks/ against an event: before a tool runs, after it ran, when you send a prompt. Copilot CLI only runs them in a folder you trusted.

A line in CLAUDE.md asks and a skill offers a procedure, but whether the agent follows them stays probabilistic. A hook is deterministic: it runs every time its event matches. When the agent ran mvn test, it puts the output through grep -E -A 3 '<<< FAIL|ERROR\] (Tests run|Failures|Errors)|\.java:\[|BUILD' and the agent only sees what comes out. IntelliJ runs the same file too, but it is not certain that the agent there gets the filtered output. You declare it like this: 

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/filter-test-output.sh" }
        ]
      }
    ]
  }
}
The script behind it 
#!/bin/bash
# Needs jq. Make it executable once: chmod +x .claude/hooks/filter-test-output.sh
# Claude Code runs this before every Bash command and hands it that call as JSON.
input=$(cat)

# The command the agent wants to run, for example "mvn test".
cmd=$(echo "$input" | jq -r '.tool_input.command')

# Only a plain mvn test or mvn verify: nothing chained on with ; & | < or >.
plain='^mvn [^;&|<>]*(test|verify)[^;&|<>]*$'

if [[ "$cmd" =~ $plain ]]; then
  # The same command, piped through grep. It keeps the failures, the summary and
  # BUILD SUCCESS or BUILD FAILURE, plus the 3 lines after each (-A 3).
  # The pipe hides Maven's exit code, so the BUILD line is the verdict.
  filtered="$cmd 2>&1 | grep -E -A 3 '<<< FAIL|ERROR\] (Tests run|Failures|Errors)|\.java:\[|BUILD'"

  # Answer Claude Code: run this command instead of the original.
  echo "$input" | jq --arg cmd "$filtered" \
    '{hookSpecificOutput: {hookEventName: "PreToolUse", updatedInput: (.tool_input + {command: $cmd})}}'
else
  # Any other command: an empty answer changes nothing.
  echo '{}'
fi
{
  "version": 1,
  "hooks": {
    "postToolUse": [
      { "type": "command", "bash": ".github/hooks/filter-test-output.sh" }
    ]
  }
}
The script behind it 
#!/bin/bash
# Needs jq. Make it executable once: chmod +x .github/hooks/filter-test-output.sh
# Copilot runs this after every tool and hands it the call and its result as JSON.
input=$(cat)

# Which tool ran, and with which command.
tool=$(echo "$input" | jq -r '.toolName')
# toolArgs is an object in Copilot CLI and a JSON string in IntelliJ.
cmd=$(echo "$input" | jq -r '(.toolArgs | if type == "string" then fromjson else . end).command // empty')

# Only a shell call that ran mvn test or mvn verify.
if [[ "$tool" == "bash" && "$cmd" =~ ^mvn.*(test|verify) ]]; then
  # Take the output the agent is about to see and keep the failures, the summary
  # and BUILD SUCCESS or BUILD FAILURE, plus the 3 lines after each (-A 3).
  # Then answer Copilot: show the agent this instead.
  echo "$input" | jq -r '.toolResult.textResultForLlm' \
    | grep -E -A 3 '<<< FAIL|ERROR\] (Tests run|Failures|Errors)|\.java:\[|BUILD' \
    | jq -Rs '{modifiedResult: {resultType: "success", textResultForLlm: .}}'
fi
# For any other tool the script prints nothing, and the result stays as it was.

A failing mvn test in exercises/step2/java prints 72 lines, and the agent now reads 18: the failing assertion, the summary and the verdict. Keep a hook fast and narrow: a broken one hands the agent an error it did not cause, and it works around that instead of writing your code.

Skills, hooks, agents and MCP servers also come bundled as plugins, installed in 1 step: /plugin in Claude Code, copilot plugin in Copilot CLI. For Java, give the agent a language server as well: the part of your IDE behind the red underlines and go to definition. Install jdtls and add the jdtls-lsp plugin in Claude Code, or an entry in .github/lsp.json in Copilot CLI. The agent then looks code up by symbol instead of with grep, and in Claude Code it also sees the compiler errors after every edit .

settings.json

Permissions

.claude/settings.json sets up the harness itself rather than what the agent knows. You commit it, so the whole team works with the same settings, and .claude/settings.local.json beside it is for you alone. The hook above is declared in it too.

Copilot CLI reads .github/copilot/settings.json, which you commit, and .github/copilot/settings.local.json for you alone. That file holds hooks, plugins and a default model, but no tool permissions: a repository cannot commit those.

The key that matters most is permissions: tool calls the agent may make without asking (allow), must ask about first (ask), or may never make (deny). A deny always wins. Allow what is safe and comes back all day, such as Bash(mvn test *), and deny what it must never read, such as Read(./.env). model picks the default model, and env sets environment variables for Claude Code itself, such as turning off automatic compaction or sending its requests through your company's LLM gateway. 

{
  "permissions": {
    "allow": ["Bash(mvn test *)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)"]
  },
  "model": "sonnet",
  "env": {
    "DISABLE_AUTO_COMPACT": "1",
    "ANTHROPIC_BASE_URL": "https://llm-gateway.example.com"
  }
}

In Copilot CLI you set them per session: --allow-tool lets a call through without asking and --deny-tool refuses it, with patterns such as shell(git:*) or read(.env). A deny always wins. Approvals you save go to ~/.copilot/permissions-config.json, on your machine only. In IntelliJ, the GitHub Copilot settings under Chat, Auto Approve list the commands that run without asking, for every project. A rule there lets a command through or makes it ask, but never refuses it. To refuse a tool call in the repository, commit a preToolUse hook that denies it: it runs for everyone who trusts the folder.

Permissions cover the agent's tools, not everything a shell command does. A rule that keeps the agent from reading a file does not stop a script that opens the file itself. That takes a sandbox: a fence at the level of the operating system around what shell commands may read, write and reach on the network. It is off by default: turn it on with /sandbox in Claude Code, or under Settings, Tools, GitHub Copilot, Sandbox in IntelliJ.
