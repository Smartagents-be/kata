An agent starts every session knowing nothing about your project, your way of working or your conventions. Arrange the repository so the agent can work efficiently in it. You get better answers, and you pay fewer tokens for them .

A few specialised files do that, and each one sits where it applies.

CLAUDE.md

The root CLAUDE.md 1 counts for the whole project. It is read at the start of every session and stays in the window for all of it, wherever the agent is working. So write what the project is about, what it is not about, and the ideas behind it. Conventions for the frontend go in the folder that holds it 2, and the backend's in its own 3, because each of these files is scoped. It only joins the context once the agent goes in there.

So keep each of them lean, and scoped to what it covers. Less entropy, less context fatigue, and a smaller bill on every turn A line earns its place when it changes what the agent writes and cannot be read off the code in a moment. The file is a briefing, not documentation.

Your own CLAUDE.md

There is one more, and it is not in the repository. ~/.claude/CLAUDE.md in your home directory is read in every project you open on this machine. So it holds how you work rather than what the project is: the language you want to be answered in, the tools you always reach for, the thing you are tired of asking for twice a day.

Nothing in here reaches your team. It sits on your machine and not in the repository, so think twice before a rule the code depends on ends up in it.

Skills

A skill can be considered a reusable high quality prompt. It is a folder under .claude/skills/ with a SKILL.md in it, holding a procedure you want followed the same way every time.

Take a job that comes back, adding an endpoint to a step's service: 

---
name: add-endpoint
description: Add a REST endpoint to a step's Spring project the way the existing ones
  are built - a controller under web/, a record for the response body, and the /api
  prefix the Vite proxy expects. Use whenever you add a route, a response shape, or a
  controller to kata/stepN/java.
---

The name matches the folder, and it is what you type after the slash. The description says what the skill does and when to reach for it, in the words somebody would actually type ("add a route", "add a controller"), because that is what the match is made against. A description reading "helps with the backend" never fires.

Keep them small. A skill may point at another rather than repeat it: the one above ends by asking for a commit, so it names commit-message instead of restating the rules for one. Detail that will not fit goes in a references/ folder beside the body, read only when it is wanted.

Be sparing with them. You pay for a description on every turn whether or not it fires, so thirty skills are a table of contents the agent reads before every answer. Two that sound alike are worse than one: if either could match, neither reliably does. Write one when you are tired of correcting the same thing, not in anticipation of correcting it.

Hooks

A hook is a script your harness runs at a fixed moment, whether or not anybody remembered to ask for it. You declare it in settings.json against an event: before a tool runs, after a file is written, when the session ends.

Which makes it the strictest of the three. A line in CLAUDE.md asks, a skill offers a procedure, and both of them depend on the agent reading and following it. A hook just happens. This one runs the formatter after every write: 

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/format-on-write.sh" }
        ]
      }
    ]
  }
}

So reach for one when the thing must happen every time and you would rather not find out that it did not.
