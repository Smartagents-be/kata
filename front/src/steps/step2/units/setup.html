A session needs the relevant instructions about your project. Put durable conventions and reusable procedures in the repository so you do not have to explain them each time .

A few specialised files do that, and each one sits where it applies.

CLAUDE.md

Step 1's unit on the session said a standing instruction belongs in the file that is read again at the start of every session. The root CLAUDE.md 1 then stays in the window for the rest of it, wherever the agent is working. Write what the project is about, what it is not about, and the ideas behind it. Conventions for the frontend go in the folder that holds it 2, and the backend's in its own 3, because a nested one only joins the context once the agent goes into its folder.

So keep each of them lean, and scoped to what it covers. Less entropy and a smaller bill on every turn A line earns its place when it changes what the agent writes and cannot be read off the code in a moment. The file is a briefing, not documentation.

A nested CLAUDE.md follows the folder layout, and some conventions cut across it: how a controller is built holds in every module that has one. Those go in .claude/rules/ 4, 1 file per topic, with a paths line naming the files they cover. Without that line a rule loads at the start of every session, like the root file. With it, the rule joins the context only once the agent reads or edits a matching file, so what is always loaded stays short.

Your own CLAUDE.md

There is one more, and it is not in the repository. ~/.claude/CLAUDE.md in your home directory is read in every project you open on this machine. It holds how you work rather than what the project is: the language you want to be answered in, the tools you always reach for, the thing you are tired of asking for 2 times a day.

Nothing in here reaches your team. It sits on your machine and not in the repository, so think twice before a rule the code depends on ends up in it.

Skills

A skill is a reusable procedure in .claude/skills/, with its instructions in SKILL.md. Its description makes it available for matching tasks; the body loads when used. That differs from standing instructions read at session startup.

Take a job that comes back, adding an endpoint to a step's service: 

---
name: add-endpoint
description: >-
  Add a REST endpoint to a step's Spring project the way the existing ones are built:
  a controller under web/, a record for the response body, and the /api
  prefix the Vite proxy expects. Use whenever you add a route, a response shape, or a
  controller to exercises/stepN/java.
---

The name matches the folder, and it is what you type after the slash. The description says what the skill does and when to reach for it, in the words somebody would actually type ("add a route", "add a controller"), because that is what the match is made against. A description reading "helps with the backend" never fires.

Keep them small. A skill may point at another rather than repeat it: a skill that ends by asking for a commit names commit-message instead of restating the rules for one. Detail that will not fit goes in a references/ folder beside the body, read only when it is wanted.

Be sparing with them. You pay for a description on every turn whether or not it fires, so 30 skills are a table of contents the agent reads before every answer. 2 that sound alike are worse than 1: if either could match, neither reliably does. Write one when you are tired of correcting the same thing, not in anticipation of correcting it.

Hooks

A hook is a script your harness runs at a fixed moment, whether or not anybody remembered to ask for it. You declare it in settings.json against an event: before a tool runs, after a file is written, when the session ends.

Which makes it the strictest of the 3. A line in CLAUDE.md asks, a skill offers a procedure, and both of them depend on the agent reading and following it. A hook just happens. This one runs the formatter after every write: 

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/format-on-write.sh" }
        ]
      }
    ]
  }
}

So reach for one when a step must happen every time and you would rather not find out that it did not. Then keep it fast and keep it narrow. That script runs on every Write and every Edit, and a broken one hands the agent an error it did not cause. The agent works around that instead of writing your code. When the thing that keeps coming back is a correction rather than a command, the patterns unit is where it goes.

Permissions and sandboxing

A starting directory focuses discovery; a worktree separates checkouts. Neither restricts capability. Claude Code permissions control tool actions, while its sandbox restricts filesystem and network access for sandboxed commands. By default, sandboxed commands can still read most of your machine, ~/.ssh included, and file tools, hooks and local MCP servers run outside the sandbox. Excluded commands and unsandboxed fallbacks need separate review. Use the harmless exercise below to verify a real restriction.
