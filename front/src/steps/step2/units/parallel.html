1 agent at a time

1 agent, 1 conversation, and you read every step it takes. No arrangement gives you more control than that. You see the file it opened before anything is written, and you answer a wrong turn while it still costs 1 sentence. The diff that comes back fits in your head. The steering unit is about what you do inside that context.

Reach for it when there is 1 thing you care about. A bug in the late-fee calculation, a query that got slow, a domain model you are still arguing with yourself about. That work is deep, and depth is where your attention buys more than throughput does. Nothing else is running, so nothing else is asking for you.

Many agents at once

Open 4 sessions and you get 4 times the output and a quarter of the attention. Nobody reads 4 runs as they happen, so you stop steering and start receiving. What you did not watch while it ran, you read afterwards, in 4 separate diffs.

It pays when the work splits cleanly and each piece has a check of its own. 4 modules, 4 builds that go green or red without you. The splitting can go to 1 agent too, which hands each piece to a sub-agent Step 1's unit on agent patterns calls that the coordinator. Give each agent its own git worktree, or they edit the same files and you find out at merge time.

The ceiling you hit first is you. 4 streams of output in an afternoon is more than anyone reads carefully, and the 10th diff gets less of you than the first did. You run out of attention well before you run out of tokens. You will not read every line any more, so let the quality gates do part of the reading for you, and have 1 more agent merge the branches and check the integration.

A worktree each

While 1 agent works, you mostly wait. 3 agents are not 3 times the work, because the waiting overlaps. Give each agent a scoped task and its own worktree, though: a separate folder on your disk, with its own checkout of the same repository, on its own branch.

Claude Code does it itself: claude --worktree loan-statement starts in .claude/worktrees/loan-statement, on a new branch worktree-loan-statement.

In IntelliJ, start a new chat with the Copilot agent and pick Worktree. Your project stays untouched until you press Apply.

Git does it too, in any tool:

git worktree add -b feat/loan-statement ../kata-loan-statement
git worktree add -b feat/native-image ../kata-native-image

What is not in Git, such as node_modules or a .env, does not come along: you install or copy that separately. A worktree separates the files, not the access. An agent with broad rights can still reach the other folder, and permissions and a sandbox handle that.

When they are done, let a separate agent bring each branch up to date. It merges main into the branch, resolves the conflicts there, runs the full gate and opens a pull request. Your CI runs the slower checks, such as the native build, and you review. Take the second branch only once the first is merged: main then holds the first change, and the gate shows whether the 2 break each other. 

In ../kata-loan-statement, merge main into feat/loan-statement and run mvn verify.
Do not change a test or lower a threshold to get it green.
For each conflict, tell me what each side wanted and what you kept.
If that is a domain decision, stop and ask me.
Then push the branch and open a pull request against main.

Once both are merged, clean up the folders:

git worktree remove ../kata-loan-statement
git worktree remove ../kata-native-image

The builder and the critic

A builder implements the change and a separate critic reports concrete defects against the requirements and check results. The builder addresses confirmed findings and repeats the review within a fixed limit. This extends the reflection pattern from the agent patterns unit. You review the resulting diff and unresolved findings.

So the whole arrangement has to be in the prompt. Nobody is there to answer once it starts, and the bar you give the critic is the last thing you get to say about what good looks like. 

Build a link shortener, in a project of its own. POST /api/links takes
a URL and answers with a code, GET /api/links/{code} hands the URL
back, and a page lists what is in there. I want it as something I
would hand a colleague: codes that do not collide, an expiry, and a
URL that gets checked. Keep it as plain as TitleController in
exercises/step1/java, which is the house style for a controller here.

You implement it. Fan out sub-agents for the parts that do not depend
on each other. Then spawn one more as a harsh critic, hand it the diff
and the running app, and tell it to attack the design, the naming and
the cases nobody thought about. It reports back. It fixes nothing.

Repeat review and repair for at most 3 rounds. Done requires a green
mvn verify and no confirmed blocking findings against the requirements.
Stop at the limit or if blocked, and report unresolved findings.
Return the diff and check results for my review; do not publish.

Strip the wording off a prompt like that and the same pieces are left.

  • Intent and a goal. What you want, and what would make it good. The second half is the one that gets left out, and it is the half the critic works from.
  • Separate briefs. Delegate independent parts and give the critic the requirements, current diff and check results. A separate review can reduce anchoring but still needs verification.
  • A critic that is harsh. Attack the design, the naming and the cases nobody thought about, report back, repair nothing. An agent asked to help will happily help you finish the wrong thing.
  • A completion condition and a limit. Require passing checks and no confirmed blocking findings. Stop after 3 review rounds and report anything unresolved for human review.
  • A gold standard. Point at something that is already good, the way the prompt above points at TitleController. "Better" is an opinion 2 agents can argue about all afternoon. "As good as this file" is a comparison.
This is the slowest and most expensive arrangement in the unit. Every round, the critic reads the whole change again and the builder rewrites what it flagged. Keep it for work that stands apart from the rest, where quality counts for more than time.

Repeated reviews can expose missed cases, but they also spend tokens and can reinforce a shared mistake. Read the final diff, check results and unresolved findings before deciding whether to ship.

1 interactive agent, background goals

1 active agent stays out in front on the build, while the other agents handle preparation, analysis and verification in the background.

The one in front you work with the way you would if it were the only one, answering it and reading the diff it hands back. The ones behind you started yourself, each on a goal of its own that takes an hour. They report to you, not to the agent in front, and need nothing from you until then. Middling control, and most days look like this.

Scaffolding a new domain is the shape of it. Behind you, one agent is writing tests against the part you settled an hour ago while another brings the docs up to date. Up front you and the agent are still arguing the model out and writing the spec that comes of it. The agents behind you are running goals rather than instructions, so you can leave them alone. The unit on long runs is where that shape is argued.
