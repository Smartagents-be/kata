Run it like production

An agent can only prove what it can run. The unit on the feedback loop had you run the whole application on your own machine, so your check keeps up. Proof asks more of that setup: the agent starts all of it itself, from 1 command, with the real database in a container, the real migrations and the build production gets. A mock that answers 200 proves the mock. What the agent cannot run, it can only claim.

Reproduce first

Before anything gets fixed, the problem has to be on the screen. Say the total on an invoice comes back 1 cent too low. Have the agent call the running app and show the wrong number, the way the customer saw it. A feature that does not exist yet gets the same treatment from the other side: say what it returns once it does, concretely enough that today's answer is visibly something else. An agent that skips this fixes the bug it imagined.

Lock it before the fix

Then the agent pins that down in something it can run again, before it touches the code. Usually a test that fails for exactly that reason. Sometimes a test is the wrong tool, and it is a curl call with the response it should give, or an action you expect to see: a row written, a mail in the queue. Run it and watch it fail. A check that has never been red says nothing about the fix. 

The total on an invoice with 3 lines comes back 1 cent too low.

Before you change any code, reproduce it against the running app and
show me the output. Write a test that fails for that reason, and give
me the curl call with the response it should return. Run both and
show me them failing.

Only then fix it. Done is that test and that curl call passing, and
mvn verify green. Finish with what you could not check.

Implement, then prove

Only now does the code change. The agent implements against the check, runs the same test and the same curl call again, and then the whole build, because a fix that turns 1 test green can turn another one red. That is the command that answers yes or no, the one the unit on long runs hands a whole run to. You read output, not an opinion. "It should work now" is not a result.

The last step is the one a command cannot take. Have the agent read the request back against what it did: what is done, what is not, and what it had no way to check. Green means the check passes. Whether the check asked the right question is still yours to read.

Test-driven, as before

None of this arrived with agents. Replicate the bug, write the failing test, then write the code: you worked that way when you typed all of it yourself, on the days you had the discipline. That is test-driven development with the reproduction in front of it. An agent told to work in that order keeps to it, on the 10th change as on the first. What used to cost discipline now costs 1 sentence in your prompt.
