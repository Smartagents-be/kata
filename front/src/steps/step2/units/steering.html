Mid-flight

You are watching it work and something is wrong. The wrong file is open, it misread what you asked, or your request left out the one thing that mattered. Escape stops it where it stands, and where it stands is what the correction costs. While it is still thinking there is nothing on disk, so you say the missing thing and it goes again from there. Once it is writing files, you are deciding what to revert as well.

Cheaper than stopping it is not stopping it at all. Type the clarification while it works and it arrives on the next turn That is the move for something small, a name it got wrong or the file you actually meant. It is the wrong move for a wrong direction, because it keeps building while your sentence waits.

The heaviest move is to stop it and throw the session away. You lose everything the run worked out, which is why you reach for it last, and it is also why it works: whatever sent it wrong goes with it. Keep it for the run that is not going the wrong way but going nowhere. There is a section on that below.

Interrupt, or go back

The obvious move is to type the correction as a new message. "Not that one, the rule lives in LateFeePolicy." It works. The agent takes the correction and carries on, and you are back on track in one turn.

It also keeps everything. The file it should not have opened is still sitting in the window, in full. Your correction sits underneath it. From here on the agent carries the wrong turn and the fix together, and re-sends both on every turn for the rest of the session You paid for the mistake once when it happened. Now you pay for it again, every message.

The other move is to go back to the message that sent it wrong and change that message instead. Most harnesses let you do this. Everything after it is dropped, and the agent starts again from your better sentence. The wrong turn is not corrected. It never happened.

Choose by asking what the work so far is worth. If it is good and you are adding something it did not know, send a new message. If it is wrong because your request was wrong, go back and fix the request. One adds to the pile. The other takes the wrong turn out of it.

Worth doing once on something small. Send a deliberately vague request, let the agent start, then go back and edit the request rather than correcting it. Ask it afterwards what it has read. The file from the first attempt is not in the answer.

When it is going nowhere

Another kind of run does not go the wrong way. The agent is in the right file, the test fails the way it failed before, and the fix it just wrote undoes the one before it. It says it sees the problem now. It said that last time. Nothing here is wrong enough to correct, so you sit through four more rounds. Every failed attempt is still in the window, and on that file they are the strongest pattern the model has to go on, so it writes another one. The loop is in the window.

Rewinding does not help here, because the message that started it was fine. Stop it and clear instead. Carry across the one thing the round produced, usually the error and the approach that does not work, and start the next session with that, the seam step 1's unit on the session tells you to pick yourself. Then change something before you ask again: paste the failing output in, name the thing it may not try, or do the awkward step by hand and give it the rest. A second attempt from a clean window beats a fifth from a dirty one.

A worktree each

Steering one agent is a full-time job. Steering three is not three times the work, because most of the waiting overlaps. A worktree is a second checkout of the same repository, on its own branch, in its own folder, sharing the same history. Give every agent one. 

git worktree add ../kata-statement feat/statement
git worktree add ../kata-native feat/native

Now two agents work at once and neither can reach the other's files. No half-finished edit from one shows up in the other's mvn test. They come back separately, you review them separately, and you merge the one that is ready without waiting for the one that is not. A run that goes wrong takes down its own folder and nothing else.

Here is the part people do not expect. Two agents are two full contexts and two bills, so parallel is not free And the second cost is yours: you now have two diffs to read that you did not write, arriving at the same time. The agents got faster. Your reading did not. Run as many as you can actually review.

Make it stop at the gap

An agent will not tell you it guessed. It hits something nobody decided, a tier that has no grace period written down anywhere, a currency the tests never name, and it does what it always does: it picks the most likely continuation and keeps going. The code compiles. The tests you have still pass. You find out at review, if you find out.

That is not a prompting mistake you can fix per request, because you do not know where the gaps are. If you did, they would not be gaps. So make the rule standing, and put it where it arrives before your first message. 

## Gaps

Never assume. When something you need is not decided anywhere in
the repository, stop, write it into `gaps.md`, and ask me.
Do not pick the most likely answer and carry on.

Three parts, and the third is the one that matters. Writing the gap down is bookkeeping. Stopping is the steering. An agent that logs its assumptions in a file and then implements them anyway has told you what it guessed, at the bottom of a diff, after the work is built on top of it.

What you get back is a short list instead of a long argument. Four questions answered in one pass, rather than four interruptions spread across an afternoon. The file is on disk too, so it outlives the session that produced it. Clear the context, hand back gaps.md, and the decisions you already made are still made.
