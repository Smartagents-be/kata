You do not write the code on this page. Not the tests, not the refactor, not the missing method, not the native build. You set the project up, you say what has to be true, and you read what came back. Everything else is the agent's.

Point your agent at kata/step2/java: a library loans domain, ports and adapters, with a late-fee rule in the middle of it. It compiles, and the one test it ships with passes, so the default build is green. It is also exactly the kind of code a quality gate exists for. One method too branchy to read, and almost nothing behind it.

Run the commands below from kata/step2/java unless the block says otherwise, because each step of this kata is its own Maven project. Set an afternoon aside.

Pre-flight

Run the check before you change anything. It goes red. The rows it prints are your three goals with the numbers you are short of. Clear one and a flag in braces takes that number's place. The machine wrote your brief, so this page does not have to. 

cd kata/step2/java
mvn verify -Pgraded

Then spend ten minutes on the repository rather than the code, on what the setup unit had you go looking for. Hand those ten minutes over as well. An agent that reads this project writes a better briefing for it than you will from memory.

One goal, three flags

Hand the module over as an outcome with the check in it: one sentence, no list of tests and no refactor plan. Then leave it alone, the way the goals unit describes. This module is small, so the wait is minutes rather than the afternoon that unit priced. The sentence you hand over is the same sentence at any size. 

> Goal: `mvn verify -Pgraded` goes green in kata/step2/java.
  Run it after every class you change, keep the default build
  green, and do not change a public signature.

If it comes back with a question instead of a diff, the rule you wrote in the pre-flight is doing its job.

One of the three does not move when you add tests. When the other two are green and that number is still short, stop writing tests and read what the row is measuring.

Two jobs, neither waits

The last two flags are independent, so run them at once. They cannot share a folder, because two Maven builds in one target/ fight over it, so give each its own worktree. The two git lines are the exception to the rule above; they run from the repository root, and each job gets its own terminal opened at that root. Both come back while you are still reading the first one. 

cd ../../..
git worktree add -b feat/statement ../kata-statement
git worktree add -b feat/native ../kata-native

In the first, the spec exists and it is failing. A tagged suite describes a method nobody wrote, and the endpoint behind it answers with a 500. Open plan mode against those tests, then check what it produces against the test names, one by one. Green tests, then call the endpoint. The code is in the response. 

cd ../kata-statement/kata/step2/java
mvn test -Pchallenge
mvn spring-boot:run
curl localhost:8080/api/loans/statement/STUDENT

In the second, nothing is failing, because nothing has been built. Compile step 2 all the way down to a native executable. That needs a GraalVM JDK on your PATH. Each attempt costs minutes, which makes it the worst place in this kata to guess, so plan it first. It compiles, it starts, and where the flag should be it prints a miss. Your plan was a piece short, and the image is the thing that tells you which piece. 

cd ../kata-native/kata/step2/java
mvn -Pnative native:compile
SERVER_PORT=8081 ./target/kata-agentic-java-step2

If a run stalls, cut the goal down. Take the one failing test, or the one line the image printed, and hand that back on its own.

The board

Each flag your run printed goes in the box beside its name, in English whichever language you are reading in.

Debrief

Five green rows say the code is right. They say nothing about how you got there, because a process leaves no exit code. Go and look.

That is the step. What is left is not about the agent at all: what changes around the work when this is how the work gets done. Step 3 is that.
