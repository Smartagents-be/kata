You have read the habits. This is where you run one. Nothing on this page grades how you worked, because a process leaves no exit code. What it grades is the thing the engineering and goals units argued you should always be able to name: a goal a build can answer yes or no to.

There is a small module in this repo built for it. Under kata/step2/java is a library loans domain, ports and adapters, with a late-fee rule at the middle of it. It compiles and it passes its one shipped test, so the default build is green. It is also exactly the kind of code a quality gate exists for: one method far too branchy to read, and almost no tests behind it.

Hand it to your agent as three outcomes, not a list of edits. Then let the build decide. Set aside an afternoon for it: the first three flags come out of one hardening pass, and the fourth and the fifth are separate jobs with their own builds.

The three goals

Every command on this page runs from kata/step2/java, because each step of this kata is its own Maven project. The goals live behind a Maven profile there, off by default so the normal build stays green. Turn it on and it measures the module against all three at once. 

cd kata/step2/java
mvn verify -Pgraded

Before you hand anything over, do the setup the setup unit asked for. Put mvn verify -Pgraded in your CLAUDE.md as the command that validates this work. That one line is what lets you give the agent a goal instead of a keystroke: it runs the check itself after each change, and the build, not the agent's word that it is done, decides when a flag is earned.

The first goal is a coverage floor: the module has to reach ninety percent line coverage, with the web and config layers left out, and the code the last two flags ask you to write left out with them, which means writing the tests it never had. The second is the complexity ceiling goals told you to hand over: no method may score above ten on cyclomatic complexity, so the late-fee method has to come apart into pieces small enough to hold in your head. Meet a goal and the build prints a flag for it, in the shape {1337-5p34k}. Miss one and it fails, and tells you the number you are still short of.

The goal that resists gaming

The third goal is the interesting one. Coverage is a proxy, and an agent will satisfy a proxy: a hundred percent of the lines can run under tests that assert nothing, and the number will still read green. So this goal is not coverage. It is whether the coverage is honest.

The build checks that by mutation testing the domain. It changes the code in small ways, a plus for a minus, a boundary nudged by one, and runs your tests again. A test suite that means something catches the change and fails. One that only executes the lines lets it through. Reach eighty percent of those mutations caught and the third flag is yours, and it is a flag you cannot earn by gaming the first.

The fourth one is built, not tuned

The three goals above all sharpen code that already runs. The fourth flag is the other half of the job: functionality that does not exist yet. The service has an endpoint for what a member tier owes, and it answers with a 500, because the method behind it was never written. 

mvn spring-boot:run
curl localhost:8080/api/loans/statement/STUDENT

Nothing describes what that method should do except the tests. They are tagged, so the normal build stays green and they only run when you ask for them. Read them as the requirement: what the statement totals, what it counts, how it splits the money per media, and what it does with a loan still inside its grace period, a lost item, and a tier that owes nothing. 

mvn test -Pchallenge

Plan it before you write it. Read the failing tests, then ask your agent in plan mode for a plan covering the whole spec, and check that plan against the tests yourself. Planning first is what keeps an agent from solving the first assertion and calling it done. Approve the plan, let it implement, and stop when mvn test -Pchallenge is green. Then call the endpoint again: it answers with the totals and the code.

The fifth resists a one-shot

The fourth flag added code that was missing. This one asks for something larger and of a different kind again: step 2's application, compiled all the way down to a native executable. It is the goals unit taken to its end, an outcome you hand over and nothing smaller. Boot's parent pom already carries the profile that builds one, so there is nothing to assemble first. What you do need is a GraalVM JDK on your PATH, and the minutes it takes to compile.

Do not one-shot it. A native build is the long-running kind the goals unit described, minutes each, which makes it the wrong place to guess and retry. Plan it first. Open plan mode and have your agent work out what inside a native image might not survive the move, and how you would find out. Read that plan, then spend the minutes once, ideally in a git worktree so your branch stays yours. 

mvn -Pnative native:compile

The plan will still be a piece short, and the image will tell you which. It compiles, it starts, and in place of the flag it prints a miss: the code lives in a resource, and a native image keeps only the resources it is told to keep, so the plain build drops it. That miss is your real spec. Read it, plan the fix it points at, a resource hint that keeps the file in the image, and build once more. 

./target/kata-agentic-java-step2

No profile prints this flag and no ordinary mvn spring-boot:run does either. It lives only in the log of a native image that was built for step 2 and told to keep its resource. Get there and the first lines it logs carry the code.

Collect the flags

The flags are English whichever language you are reading in, like every answer this course asks you to type. Paste one in, and if it is the real one the box turns green and stays that way.

That is the step. What is left is not about the agent at all: what changes around the work when this is how the work gets done. Step 3 is that.

If you get stuck, the honest move is the one the goals unit named: give the agent the goal and the command that checks it, run it in a git worktree, and read the diff it comes back with rather than the report.
