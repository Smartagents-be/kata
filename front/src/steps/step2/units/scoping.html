Scoping is deciding how much work goes into one request. Too little and you spend the day steering. Too much and you get a large, plausible answer that is wrong somewhere in the middle, and finding where costs more than writing it yourself.

This kata is built that way on purpose. Each step adds one topic on top of the code the previous step left behind, and a request is almost always "add the next step" rather than "build the finished thing". The intermediate shape is what you are there to learn.

A well-scoped task has a visible edge: you can say what is in it, what is deliberately left out, and how you will know it is done. When you cannot say those three things, the task is not ready to hand over yet.

Where you start the session

The first scoping decision happens before you type anything. It is the folder you open the agent in. Take the articles service from the previous unit: start in apps/article/ and that domain is the whole world. Start at the repository root and every domain is.

Two sessions that belong inside the domain: 

cd apps/article && claude
> PublishArticle leaves the headline unset when the draft flag is on.
  Fix it, and cover it with a test.

cd apps/article && claude
> Give the S3 archive adapter a retry with backoff. Three attempts,
  and the Archive port keeps the signature it has.

Neither prompt says which domain it means, because the folder already said it. That is the gain, and it is bigger than the shorter sentence suggests. Every file the agent lists, greps and opens is inside one domain, so the wrong file is not on the table and the reading it does per turn stays small.

The warning goes with it: you may be working without half your instructions. The CLAUDE.md, the permissions in settings.json, the hooks and the skills all live at the repository root, and a session started two levels down does not go looking for them. That is what the .claude symlink in the previous unit's drawing is for. An agent running without your project's rules never mentions it. It writes code that looks fine and quietly ignores your conventions.

You give up the wide view as well. Anything that touches a second domain, the root pom.xml, or a *-context jar you depend on is outside the folder you opened. The agent will reason about it anyway, from memory of what it has seen, which is the expensive kind of wrong.

Worth doing once in a domain folder: ask the agent what it read before your first message. If your CLAUDE.md is not in the answer, the symlink is not doing its job.

Starting at the root is the other side of the trade. Everything is in reach: the whole CLAUDE.md, the hooks, the skills, every domain and the poms that tie them together. Nothing is narrowed down for you either, so the prompt has to do that job. "Fix the headline bug" at the root sends an agent reading through apps/ until it finds something that looks like one.

So name the target yourself. "In apps/article/article-domain, PublishArticle leaves the headline unset when the draft flag is on" costs you five words and buys back the focus the folder was giving away for free. A domain-driven layout is what makes that cheap, because the name of the folder is the name of the thing.

The rule is short. One domain, and you know which one: open the agent inside it. Two domains, the root pom, or you are still hunting for where the thing lives: open it at the root and say the domain out loud.
