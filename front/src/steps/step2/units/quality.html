An agent will tell you the change is done. That sentence is not evidence. Quality management is arranging things so something other than the agent gets to decide whether the work is finished.

Here that is mvn test on the Java side and npm run build on the frontend, since the build is also the type check. Both are cheap, both run on demand, and every step of this kata is expected to leave them green. A test that fails is worth more than a paragraph explaining why the code is correct.

Automation stops short of taste, though. Whether a name is right, whether the change belongs in this file, whether the abstraction earns its keep: that is still you reading the diff. Set up the checks so you spend your attention on the parts a check cannot reach.

Write the standard down where the agent reads it

A convention only holds if the agent meets it before it writes, not after you reject the diff. Some of that is a testing standard. In this repo a test is a *Test.java file, it asserts through AssertJ rather than JUnit's Assertions, and a table of cases is a @ParameterizedTest with a @CsvSource. Turn that into a skill and a new test comes out in the house style the first time.

The shape of the project is the same kind of rule. A new step here is a folder under front/src/steps/, one HTML file per unit, an en.json and an nl.json, an index.tsx, and a line in steps/index.ts. That is a scaffolding skill, and the unit on repeating patterns already argued the better version of it: the skill runs a script, so step 3 and step 7 come out identical instead of similar.

Do not write the whole CLAUDE.md from memory either. Point the agent at the repository and ask it to draft the briefing: the Java version, the AssertJ rule, the one-way import between steps and shared. It reads the code more evenly than you remember it. Then you cut it back to what changes what the agent writes, because a file paid for on every turn earns its length or loses it.

Pick metrics that carry weight

Coverage and cyclomatic complexity are worth enforcing because a build can print them. Put a ceiling on both. No method above ten branches, and a coverage floor on the module you are touching, both wired into mvn verify so the number fails the build rather than sitting in a report nobody opens.

Be smart about what the number is really telling you, though. A metric is a proxy, and an agent will satisfy the proxy. A hundred percent coverage from tests that assert nothing is green and worthless, so pair the percentage with a look at whether the tests can fail. A low complexity score means nothing if a method was split in two to move the branches around. The number is the floor of quality, not the proof of it.

Two habits an agent gets wrong on its own belong in CLAUDE.md next to the numbers. It over-comments, narrating what the line already says, so ask for comments that explain why and cut the rest. And it under-logs, so name where a log line belongs: at the boundary of a use case, on the path a request takes, not inside a getter. Both are hygiene a reviewer should never have to ask for twice.
