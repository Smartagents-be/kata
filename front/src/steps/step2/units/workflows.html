How you hand the work over matters as much as what you hand over. A workflow is the shape of the whole run: how much you write down before the agent types anything, and what tells you afterwards that it worked.

What follows runs from cheapest to most deliberate. The further down you go, the more you settle before any code exists and the less you have to re-read when it arrives. That trade is the decision you are actually making.

Naive

Almost everybody starts here. Ask for the feature, skim what comes back, run it. When it breaks, paste the error and ask for a fix. Nothing is written down, because nothing was decided. The engineering unit called this vibe coding and argued against it.

It still has a place, and the place is real. A site for the baker on the corner. A trial version built to find out whether the idea holds up at all. A one-line change in an otherwise careful project: a padding, a log line, a column that should have been nullable. This is deliberately not structuring or restructuring.

A throwaway that turns out to have users is recoverable. Point the agent at what already runs, ask it to write the specs the code implies, and read them for what it got wrong. You are retrofitting the workflow you skipped, and it costs less than the rewrite you were bracing for.

Plan-based

One step up costs one keystroke. Ask for a plan instead of the change, every time, not only when the task looks hard. Step 1's unit on the prompt introduced plan mode as meta-prompting the provider already built for you. Using it once is a trick. Using it by default is a workflow, and it buys better work at the price of waiting longer for it.

The plan is not the part worth having. The agent interviews you and its questions are the ones you skipped: which tier gets a grace period, what happens when the list comes back empty, whether this belongs in the domain at all. You answer them before a line exists, which is what you would have done designing it yourself. The workflow put you back in the design.

Spec-driven

Write the feature down before anybody builds it, one markdown file per feature, kept in the repository beside the code. What it does, in detail. What it deliberately does not do. The acceptance criteria somebody can hold the result to, and the specs this one depends on. The out-of-scope half earns its place fastest, because that is where an agent invents things.

What grows out of that is a living document rather than a folder of closed tickets. An agent opening the repository reads the spec beside the code and knows what the code was meant to be. Once there are more specs than anybody can hold in their head, add an index.md with a line each Finding the right one then costs one file instead of twenty.

You do not write these cold either. Describe the feature in two sentences, ask for the spec in your format, then cut what the agent invented. Reviewing a draft is faster than facing an empty file, and a draft that guessed wrong shows you exactly what you never decided.

Audit-driven

Build however you like, then ask for the audit. The agent reads the files under scrutiny and writes audit.md: is this complete, is it secure, does it follow the style the repository already uses. That is the reflection pattern from step 1's unit on the harness, aimed at a project instead of at a single answer.

Ask for a format or you get an essay. A table holds it down to what you can act on: the topic, where it lives, how solid it is, and what to do about it. This repository has one at the root, and it is what the course gets rewritten from.

Flip it to markdown and nothing changes but the rendering. An audit is a file in your repository, so it diffs and gets reviewed the way the code does, and it is still there next week when you have forgotten which row you were on.

Then work the table. Worst row first, fix it, run the audit again. The solid row with nothing beside it counts as much as the rest, because that is one thing you can stop carrying around. And the whole document stays short enough to read in one sitting, which is the difference between a report and a plan.

Pick per task

None of these is a camp you join. A throwaway prototype on Friday and a written spec for the payment change on Monday is one engineer working sensibly. Plan mode sits inside spec-driven work, where a good spec is what makes the plan short. An audit is worth running over any of them.

Nothing on that drawing gets shorter. The work moves to the front or to the back, and what moves with it is whether anything is left on disk when the session ends.

So read the task before you pick. How long does this code live, what does it cost to get wrong, how much of the diff will you have to read yourself. Then take the cheapest workflow that answers those. No method is perfect, and deciding between them is the engineering.
