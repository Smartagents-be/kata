How you hand the work over matters as much as what you hand over. A workflow is the shape of the whole run: how much you write down before the agent types anything, and what tells you afterwards that it worked.

The further down this page you go, the more you settle before any code exists, and the longer it is before anything runs. Where you stand on that line is the choice this unit is about.

Naive

Almost everybody starts here. It is the vibe coding the unit on domain language and structure argued against: ask, skim, run, and paste the error when it breaks. Nothing is written down, because nothing was decided.

It still has a place. A site for the baker on the corner. A trial version built to find out whether the idea holds up at all. A 1-line change in an otherwise careful project: a padding, a log line, a column that should have been nullable. Nudging is not restructuring.

A throwaway that turns out to have users is recoverable. Point the agent at what already runs, ask it to write the specs the code implies, one per feature, and read them for what it got wrong. You are retrofitting the workflow you skipped, and it costs less than the rewrite you were bracing for.

Plan-based

1 step up costs a mode switch. Ask for a plan instead of the change, every time, not only when the task looks hard. Step 1's unit on the prompt introduced plan mode as meta-prompting the provider already built for you. Using it 1 time is a trick. Using it by default is a workflow, and it buys better work at the price of waiting longer for it.

The plan is not the part worth having. The agent interviews you and its questions are the ones you skipped: which tier gets a grace period, what happens when the list comes back empty. You answer them before a line exists, which is what you would have done designing it yourself. The workflow puts you back in the design.

Spec-driven

Write the feature down before anybody builds it, 1 markdown file per feature, kept in the repository beside the code. What it does, in detail. What it deliberately does not do. The acceptance criteria somebody can hold the result to, and the specs this one depends on. The out-of-scope part earns its place fastest, because that is where an agent invents things.

The specs grow into a living document, and a folder of closed tickets never does. An agent opening the repository reads the spec beside the code and knows what the code was meant to be. Once there are more specs than anybody can hold in their head, add an index.md with a line each Finding the right one then costs 1 file instead of 20.

You do not write them from scratch. Describe the feature in 2 sentences, ask for the spec in your format, then cut what the agent invented. Reviewing a draft is faster than facing an empty file, and a draft that guessed wrong shows you exactly what you never decided.

Defer

Mid-task, the agent reports something outside the task: a bug it walked past, a refactor it would suggest. Chase it now and your session is about 2 problems instead of 1.

So defer it. Tell the agent to write what it found into a markdown file, 1 entry per finding, with where it lives and why it matters, and carry on with the task you started. A report at the end of a run goes the same way: its suggestions wait in the file instead of in your head.

Pick the file up in a separate session, or next week. Triage it like any other input: drop what does not hold, turn what does into a spec or a one-shot prompt, and resolve it through whichever workflow above fits. Nothing got lost, and nothing got in the way.

Audit-driven

Build however you like, then ask for the audit. The agent reads the files you point it at and writes audit.md: is this complete, is it secure, does it follow the style the repository already uses. That is the reflection pattern from step 1's unit on agent patterns, aimed at a project instead of at a single answer.

Ask for a format or you get an essay. A table holds it down to what you can act on: the topic, where it lives, how solid it is, and what to do about it. This repository has one at the root, and the course gets rewritten from it.

Flip it to markdown and nothing changes but the rendering. An audit is a file in your repository, so it diffs and gets reviewed the way the code does, and it is still there next week when you have forgotten which row you were on.

Then work the table. Worst row first, fix it, run the audit again. The solid row with nothing beside it counts as much as the rest, because that is 1 thing you can stop carrying around.

Pick per task

None of these is a camp you join. A throwaway prototype on Friday and a written spec for the payment change on Monday is 1 engineer working sensibly. In spec-driven work you always plan from the spec, even for a small change, and a good spec keeps that plan short. An audit is worth running over any of them.

Nothing on that drawing gets shorter. The work moves to the front or to the back, and with it moves whether anything is left on disk when the session ends.

So read the task before you pick. Ask how long this code will live, and how much of the diff you will have to read yourself. Then take the cheapest workflow that answers those. Deciding between them is the engineering. The next unit is about how fast you find out whether the work holds.

1 project usually climbs through all of them and then drops back down, 1 audit row at a time rather than for the whole project. Whatever those fixes change goes back into the specs, or the specs quietly stop describing what you shipped.
