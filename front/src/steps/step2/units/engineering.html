Good agentic projects start with good software engineering. That is the whole line between vibe coding and agentic engineering, and it is worth being blunt about which side you are on. Project evolution put you on the other side of it for an hour, on a version built to be thrown away, and that is the one place the line does not hold.

Vibe coding is asking for a feature, skimming what comes back, and running it. When it breaks you paste the error and say "fix this". That works for about an hour. Then the fixes start breaking each other, nobody has read the code in a while, and you are steering a system you no longer understand. The loop feels productive right up to the moment you cannot answer a simple question about your own repository.

Software engineering has always been a craft. A problem arrives from the business, you break it down until each part is small enough to be sure about, and you pour the result into a process that runs as code. None of that changes when an agent does the typing.

Domain-driven design

Folders and concepts carry the same names the business uses. Hexagonal architecture sorts the rest: the domain in the middle, the machinery behind adapters, and the direction of a call as a folder you can point at. Both give you the logical shape, and a logical shape is what you can prompt against Ask for a feature on articles and the agent knows where to look before it opens anything. Nothing above adapter/ names Postgres or S3, so swapping the database out is one folder's work.

That is a bigger lever with an agent than it ever was with a team. A model reads your repository as tokens and predicts what comes next. Plain English is what it predicts best, which is what step 1's unit on tokens showed.

Use the correct language

Name the thing you want. "Put a repository in front of this JDBC call" lands somewhere specific. "Clean this up a bit" lands in the statistical middle of every cleanup ever written. Design pattern names, layer names and the vocabulary of your domain are compression. They keep an agent on the task instead of on its own reading of what you meant. That is also what separates an app built in half a day from one you can put in production.

Quality gates

Skills and hooks turned up in project setup as things a project holds. This is where you put them to work. Line coverage, mutation coverage and a Sonar reliability score still tell you whether software is fit to ship. They also hand an agent an invariant, something fixed to hold itself to while it works Each of them is a proxy, though, and an agent will satisfy a proxy rather than the thing behind it. The gate worth wiring in is the one that is expensive to fake.

Wire that into the run rather than into your memory. A hook fires when the agent says it is finished, mvn verify runs the analysis, and a number under the floor comes back as a failure it has to answer for. The same rule written into CLAUDE.md is a request. This one runs whether the agent remembers it or not.
