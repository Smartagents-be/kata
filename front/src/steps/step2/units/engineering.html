Good agentic projects start with good software engineering. That is the whole line between vibe coding and agentic engineering, and it is worth being blunt about which side you are on.

Vibe coding is asking for a feature, skimming what comes back, and running it. When it breaks you paste the error and say "fix this". That works for about an hour. Then the fixes start breaking each other, nobody has read the code in a while, and you are steering a system you no longer understand. The loop feels productive right up to the moment you cannot answer a simple question about your own repository.

Agentic engineering is a different job. You aim the harness at exactly what you want, you check the work while it is happening, and you correct it there rather than after. The skills involved are the ones you already have. What changes is that you are applying them to output you did not type.

Say it in the language of the craft

Name the thing you want. "Put a repository in front of this JDBC call" lands somewhere specific. "Clean this up a bit" lands in the statistical middle of every cleanup ever written. Design pattern names, layer names and the vocabulary of your domain are compression: one word carries a structure the model already knows in detail.

Then watch it work. An agent that is reading the wrong file, or has decided to introduce a factory you did not want, tells you so in its first few steps. Stopping it there costs a sentence. Letting it finish and then asking for a rewrite costs the whole diff, twice, and you read it twice as well.

Make the checks part of the work

Ask for tests with the change, not after it. mvn test is one command, so there is no excuse for a feature arriving unproven. Ask what the coverage of the class you just touched actually is, and which branch nobody exercised. Ask for the cyclomatic complexity of a method that has grown three levels of nesting, then ask for it to come down.

Those requests do not belong in a prompt you retype every morning. They belong in CLAUDE.md, where they apply to every change without you asking. A standard the agent reads before it starts is a standard you stop enforcing by hand.

Structure is the biggest lever

The techniques you already trust work here, and domain-driven design is the clearest example. Split the code into domains and keep each one whole: its language, its rules and its data in one place, named after what the business calls it. An agent asked to change how orders are priced should find everything it needs in one folder.

Ports and adapters do the other half. The domain talks to interfaces it owns, and the database, the HTTP layer and the message broker sit behind adapters that implement them. That is a wall, and walls are what stop a change to pricing from quietly growing a JPA annotation. This kata has a small version of the same idea: steps may import from shared, never the other way round.

On disk that is a folder per domain, and the same four Maven modules inside every one of them. Here is a service that publishes articles, with one domain opened up. Nothing below exists in this repo, so read it as the shape.

Start with the modules. article-domain is the code itself: the aggregate, the use cases and the adapters, in one module because they are one domain. article-configuration wires Spring and owns the Liquibase changelog. article-bootstrap holds the only main method, and article-context is the small jar other domains are allowed to depend on.

Around those sit the three things that make it a domain of this platform, and none of them are decisions. A BOM listing the four modules, an entry in the root pom.xml, and a .claude symlink so an agent working in apps/article/ reads the same instructions as everywhere else. It is identical in every domain, which is why creating one should be a script you run rather than a conversation you have.

Now read the domain module from the inside out. domain/ holds the aggregate, the rules that guard it, and the interfaces it needs from the world outside. ArticleRepository and Archive are ports, and the domain wrote both of them in its own words. application/ is one class per use case, calling those interfaces and nothing else. adapter/ is where HTTP, JPA and S3 live, each class implementing a port that was declared above it.

Every dependency in that picture points inward. ArticleRow knows about Article, and Article has never heard of ArticleRow. Swap Postgres for something else and only adapter/persistence/ changes. That is also why author/ is drawn beside it: the shape repeats, so a new domain is a new folder rather than an argument about where things go.

Three things follow, and the third surprises people. Boundaries keep the agent focused, because the code it must not touch is not in front of it. They let you scope a task precisely, because you can name the domain and mean it. And they cut your token cost, because a well-bounded task reads five files instead of fifty, on every turn, for the length of the session.

A useful diagnostic: ask an agent to make a change and watch how many files it opens before it writes anything. If it is wandering, that is your architecture answering the question, not the model.

None of this is new. Tests, boundaries and clear names were already how you kept a large codebase from turning on you. Agents did not change the practice. They raised the price of not having it, because code now arrives faster than anyone can read it.
