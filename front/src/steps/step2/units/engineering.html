Good agentic projects start with good software engineering. That is the whole line between vibe coding and agentic engineering.

Vibe coding is asking for a feature, skimming what comes back, and running it. When it breaks you paste the error and say "fix this". For a small project with little domain logic, that works fine. For complex business processes it works poorly and gets expensive fast, because there are no clear rules or because the agent picked the architecture and the tools itself. The fixes start breaking each other, and eventually you cannot answer a simple question about your own repository.

Software engineering has always been a craft. A problem arrives from the business, you break it down until each part is small enough to be sure about, and you pour the result into a process that runs as code. None of that changes when an agent does the typing.

Domain-driven design

Folders and classes carry the names the business uses. Iban is an IBAN and payments/ is where payments live. Ask for the IBAN to be validated on every payment and your sentence has already named the file

Clear domain names make instructions and searches more precise. The IBAN in your request points towards Iban in the tree. That helps the agent locate relevant code.

Vertical slices

A layered application invites you to build it a layer at a time: all of the data access, then all of the business logic, then the screens. Nothing runs end to end until the last layer is in, and that is the first time you learn whether the layers fit. Cut it the other way: 1 use case with everything it needs, from the screen down to the table, running before you start the next one. That is a vertical slice.

Put the slices that belong together in 1 module: a business capability, named after what the business does. payments/ holds the form, the endpoint, the rules and the table for payments. Every slice is 1 turn of the feedback loop, and the module keeps that turn short, the way the unit on quality gates asks: mvn -pl payments verify answers about the part you changed and nothing else.

A slice runs from the screen to the table, and through the pipeline to production. Build one with an agent and you have to judge every layer it touches: the form, the endpoint, the build, the deployment, the access rules. You do not have to write all of that yourself, but you do have to see when it is wrong. That asks for a T-shaped profile: deep in 1 field, and enough of the rest to judge it.

Hexagonal architecture

Inside each module the domain sits in the middle. Around it, application/ holds the use cases in usecases/ and the ports they reach the outside through in ports/. Everything that talks to the outside world lives in adapters around that: what calls in under adapter/incoming/, what the use cases call out to under adapter/outgoing/. No class outside adapter/ names Postgres or S3. So the code that talks to the database sits in 1 folder, and swapping the database starts there.

What that saves with an agent is the search. It opens application/usecases/ for a use case and adapter/outgoing/ for the thing that talks to S3, instead of reading half your repository into the context first .

It also makes each part testable on its own. The domain depends on nothing, so you test its rules without a database or a mock. A use case only sets the order of the steps, and its test swaps each outgoing port for an in-memory version. Only an adapter needs the real Postgres, and that is what an integration test is for.
