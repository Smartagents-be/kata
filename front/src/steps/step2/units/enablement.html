Run it on your own machine

Feedback is fastest when the whole application runs on your own machine. Frontend, backend, the database in a container, with data in it that covers the everyday cases and the edge cases. Then you look at what your users see, and a wrong column shows up as a wrong column instead of a field name in a response body. The agent writes the change in seconds, and your check on it has to keep up.

Give the agent the same setup: the running app, and the browser server from step 1's unit on the agentic loop. Now it checks its own work before handing it back. It opens the page, sees the wrong column and fixes it in the same pass .

Put all of it in a development container, and you and the agent work with the same machinery. It starts from 1 command, with the real database, the real migrations and the build production gets. A test against a mock only tells you the mock works. What the agent cannot run, it cannot check.

A development container

The kata ships one, in .devcontainer/. The Dockerfile builds an image with the JDK, Maven, Node, Claude Code and Copilot CLI in it. Your IDE connects to the container (VS Code and IntelliJ both can), so the editing, the build and the agent all run inside it. What has to outlive the container, such as your login and Maven's downloads, sits in a volume that the next container mounts again. Everything else goes when the container does.

The container is also a sandbox for the agent. It sees what is in the container and nothing else on your laptop: not your home folder, not your SSH keys. The sandbox has gaps, though. The agent can still reach the internet. And if you share your laptop's folder with the container instead of cloning the repo into it, what the agent writes there runs on your laptop at your next build.

Reproduce first

Before anything gets fixed, the problem has to be on the screen. Say the total on an invoice comes back 1 cent too low. Have the agent call the running app and show the wrong number, the way the customer saw it. Without that, it fixes the bug it guessed at, not the one the customer hit. A new feature starts the same way: write down what it should return, concretely enough that you can see today's app does not do that yet.

Lock it before the fix

Before the agent touches the code, it pins the problem down in something it can run again. Usually that is a test that fails for exactly that reason. Sometimes a test is the wrong tool. Then it is a curl call to the running app, with the response it should give, or an action you expect to see: a row written, a mail in the queue. Run it and watch it fail. A check that has never been red says nothing about the fix. 

The total on invoice INV-2041 comes back 1 cent too low: 3 lines of
10.00 each, and the invoice says 29.99. @InvoiceService.java

Before you change any code, call GET /api/invoices/INV-2041 on the
running app and show me the response. Then write a test that fails for
that reason, the way InvoiceServiceTest covers the discount case. Run
it and show me it failing.

Do not change how a single line is rounded: the VAT report reads those
amounts.

Only then fix it. Done when that test passes, the same call returns
30.00, and mvn verify is green. Finish with the files you changed, 1
line each, and what you could not check.

Implement, then prove

Only now does the code change. The agent runs the same test and the same curl call again, then the whole build, because a fix that turns 1 test green can turn another one red. Then have it read the request back: what is done, what is not, and what it had no way to check. Green means the check passes. Whether the check asked the right question is still yours to read.

Test-driven, as before

None of this arrived with agents. Replicate the bug, write the failing test, then write the code: you worked that way when you typed all of it yourself, on the days you had the discipline. That is test-driven development with the reproduction in front of it. An agent told to work in that order keeps to it, on the 10th change as on the first. What used to cost discipline now costs 1 sentence in your prompt.

T-shaped

An agent implements faster than you, so what it asks of you moves up a level: the T-shaped profile from the unit on domain language. Say the change comes back with a database migration in it. You do not have to be able to write it, but you do have to notice that it drops a column 2 other services still read. The agent handles the detail for everyone alike, so knowing the detail is worth less than it was. Knowing what good software engineering looks like is not.

Where the day goes

Coding by hand is dead. David Heinemeier Hansson, who created Ruby on Rails, said in his Rails World 2026 keynote that his company is "done writing code by hand". So count where the hours go. They go on driving the system end to end and reading whether it did what you wanted. The steering unit covers what you do while a run is in flight. This is the other half, the part after it comes back. It is most of your week.

Read every plan and every diff against the same questions:

  1. Which files did it touch, and did you expect each one?
  2. What did it assume that nobody told it?
  3. What proves it works: a test you watched fail and then pass, or its word?
  4. Is it small enough to review in one sitting?

Look hardest at changed tests. An agent that cannot make a test pass can weaken the assertion or mock away the thing under test.

The hours that are left go on thinking. Go through the implementation details, argue both sides of them, and come out with a design decision you could defend. A decision you did not make is one the agent made for you. How many of those runs you have going at once is the next unit's question.
