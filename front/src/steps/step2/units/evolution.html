A project used to arrive in a few large moves. You designed for weeks and built a prototype. Then you demoed it to your client or the business, and back came new ideas, extra functionality, and an expensive refactor.

When a version costs an hour, that feedback arrives while it is still cheap. Take a small step, read what came out, correct it, aim again. You are never guessing more than one step ahead, and you aim from where the work actually is instead of from where the plan said it would be.

A prototype starts a conversation

The first version exists to get a reaction out of somebody. Build three takes on the same screen in the time one argument about it would cost, put them side by side, and watch which one people start talking about.

Put several options in front of people and you find out fast what works, what has to change, and what is missing entirely. Act on that. Take the strongest parts of each one across.

Walking skeleton

Start building with a very rough version. Keep the details out, because every one of them costs extra What the first version does have to get right is the shape: the right characteristics, a label of its own, a place in the application structure, and a result that actually comes back.

This is how the course looked at first. The idea of a sidebar, a question and answer section, some explanation. What it did not have yet: branding, the colours, the styling, a few extras like the settings, and a better way to get around.

That is how it grew, too. A lot of the content went in first, and those things arrived after. Ask an agent for a whole system and you get a plausible one. Ask it for the next change to a running one and you can check the answer.

Adding details

None of this is new. Traditional software engineering works the same way. KISS. The detail work comes after. Branding. A filter on a list. An extra attribute on the model, and every place that has to read it.

That is the same course with the details in. Which side of that line a change falls on is yours to decide as the engineer. Work out the bare minimum that makes something run and matter to the project. The rest is detail work.

Every detail you pull forward is paid for now, and it is one more thing that can break while the shape is still moving. Leaving them too long has a price of its own. Add them late enough and fitting them in breaks what already worked, so you are paying for a regression instead of for functionality.

As a rule of thumb, a detail should not cost you more than an hour. Longer than that and it was not a detail, it was the next step. You get a feel for where that line sits the more you work this way.

Every one of those small loops opens the same way, with an agent that knows nothing about your project. What it reads before your first message is the next unit.
