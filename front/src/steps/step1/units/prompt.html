Everything you send the agent is a prompt. It is usually the smallest part of what the model receives, much smaller than the session. But it is the most valuable part, because only the prompt carries your intent.

You rarely send just 1. Some are new questions you type, others are answers to questions the agent asks you about the task . Write "grill me" and the agent does that on purpose: it questions you about your plan, 1 question at a time, until you agree on it. Matt Pocock also publishes this as a skill.

Instruction

A prompt is an instruction, so say what you want the model to do. Every inaccuracy in it compounds once the agent starts work. Putting one right while it is already working is steering, which comes later.

Not every prompt needs all 6. fix it is a goal and nothing else, and for small, well-scoped work that can be enough. The less you fill in, the more the agent decides on its own. The one people leave out is the last: a check the agent can run itself, which step 2's unit on long-running goals and cost takes further.

Reasoning level

The reasoning level (effort, in Claude Code) sets how much work the model puts into a task: how long it thinks, how many files it reads and how much it checks before it comes back to you. Claude Code’s /effort sets it from low to max on supported models, and Opus 5.5 and Sonnet 5.5 default to medium. In Copilot you set it in the model picker. It does not supply requirements you never gave.

That is not the same as picking another model. A model is a fixed set of weights, set during training. What it knows and what it can do live there, and a larger model can do more. Your prompt and context steer those weights but never change them. Effort makes the same model work harder; it does not make it smarter. A rule of thumb from Anthropic: if the agent had all the context, clearly tried and was still wrong, pick a more capable model. If it skipped a file or did not run the tests, raise the effort.

Higher effort can spend more tokens and time. Reasoning tokens are billed as output The chart holds answer length constant to show that cost; real answers and tool use can change too. Use higher effort when the task warrants it, and clarify a vague request first.

That thinking also covers the agent's own moves: which file to open next and what to hand itself as input for the step after that.

Meta-prompting

Meta-prompting is letting a model write the prompt. You say roughly what you want, it writes the instruction, and you read it back and fix the parts it got wrong.

Spend an expensive model on this. Writing a prompt is a few hundred tokens next to executing one, so the top tier is cheap here Which tiers there are, and what they cost, is the unit on the model.

Plan mode

Plan mode is meta-prompting the provider already built for you. In a terminal, press Shift+Tab until the status says Plan, or start a prompt with /plan. In IntelliJ, pick Plan in the agent picker. The agent reads around without changing anything, usually asks you about whatever is still open, hands back a plan, and waits. You edit it (in Claude Code, Ctrl+G opens it in your editor), ask for another pass, or approve it. The agent waits for your approval before carrying out the plan. That makes it a built-in checkpoint: you review the solution before anything is carried out.

Plan mode is not always needed. If you already know exactly what needs to change in 1 file, the decisions are made. A plan only puts those decisions in writing for you to approve. Ask the agent to make the change directly .

1 ask, not 3

Group changes to the same part of the application into 1 request Every follow-up sends the earlier questions and answers to the model again. That uses extra tokens and increases the cost. Earlier answers and intermediate versions also remain in the window, even when you no longer need them.

State exactly what the model should do

The less you say, the more the model has to fill in itself. Compare "fix the login" with this ask to the same model: "Make TitleController return a 404 when the catalogue comes back empty. Look at @TitleController.java and @Catalog.java. Do not change Catalog: the problem is how the controller handles an empty result. Done when mvn test is green, with a test for an empty catalogue." That ask names the goal, the files, a limit with its reason and when it is done. With "fix the login" the agent may get there too, but it first has to work out what is wrong and where. That costs more tokens and time, and it can guess wrong.

Say where the job stops and explain why. “Do not throw an exception, because a user that does not exist is a normal outcome” supplies both a constraint and its purpose. The reason helps the agent spot related mistakes, such as returning null. Verify that it followed the constraint.

Few-shot prompting

Point at code that already does it right. "Do it the way OrderController handles an order that does not exist" hands the agent the structure, the names and the libraries in one go It copies an example more faithfully than any description you could write of it. Giving several examples in the prompt is few-shot prompting. With 1 example, it is called one-shot prompting.

Output format

Specify how you want the answer presented. When you ask the agent to review code, add something like: "List the problems you find. For each problem, include the file, line number and a short explanation" That lets you go straight to the relevant place in the code. If you want the result as a file, say so: "Write it to review.md." And if you have a fixed shape, pass the template along, for example the headings ## Problem, ## Cause and ## Fix. The agent then fills it in rather than choosing a shape of its own.

If you want to choose first, ask for options rather than 1 fix: “Give me 3 possible fixes, each with its pros and cons. Do not change anything yet.” Then pick one and have the agent apply it. In plan mode the agent changes nothing until you approve.

Paste the real error

Share the error message, the command you ran and when the error occurs. Include only the relevant stack trace lines, such as those pointing to your own code If the full output is in a log file, give its path so the agent can search it for the relevant details. Ask the agent to investigate and fix the cause.

What no longer works

Typing “think hard” or “think step by step” is ordinary prompt text. Recent models reason on their own, and how thoroughly is what the reasoning level sets. Claude Code recognises only ultrathink, which asks for deeper reasoning on that one turn. A role such as “senior Java engineer” steers tone and style, but does not make the answer more correct. Concrete requirements, current information and a check give you something to verify.

Capital letters and exclamation marks are unnecessary too. Recent models already follow instructions closely. Words like "MUST" and "NEVER" can make the agent apply a rule too rigidly, including in situations you did not intend. State the instruction 1 time, in a normal sentence with a reason: "Use constructor injection so the class is easy to test."
