Everything you send the agent is a prompt. It is usually the smallest part of what the model receives, much smaller than the session. But it is the most valuable part, because only the prompt carries your intent.

You rarely send just 1. Some are new questions, others are answers to questions the agent asks you about the task Write "grill me" or "interview me" and the agent questions you about your plan on purpose, until you agree on it. Matt Pocock also publishes this as a skill.

Instruction

A prompt is an instruction, so say what you want the model to do. Every inaccuracy in it compounds once the agent starts work. Putting one right while it is already working is steering, which comes later.

Not every prompt needs all 6. fix it is only a goal, and for small, well-scoped work that can be enough. People most often leave out the last part: a check the agent can run itself, which step 2's unit on proving your work takes further.

Reasoning level

The reasoning level (effort, in Claude Code) sets how much work the model puts into a task: how long it thinks, how many files it reads and how much it checks before it comes back to you. Claude Code’s /effort sets it from low to max on supported models, and Opus 5.5 and Sonnet 5.5 default to medium. In Copilot you set it in the model picker. It does not supply requirements you never gave.

That is not the same as picking another model. A model is a fixed set of weights, set in training: what it knows and can do lives there, and a larger model can do more. Your prompt and context steer those weights but never change them. Effort makes the same model work harder, not smarter. Anthropic's rule of thumb: if the agent had all the context, clearly tried and was still wrong, pick a more capable model. If it skipped a file or did not run the tests, raise the effort.

Higher effort usually spends more tokens and time, and reasoning tokens are billed as output Raise it when the task warrants it, and clarify a vague request first.

That thinking also covers the agent's own moves: which file to open next and what to hand itself as input for the step after that.

Meta-prompting

Meta-prompting is letting a model write the prompt. You say roughly what you want, it writes the instruction, and you read it back and fix the parts it got wrong.

Spend an expensive model on this. Writing a prompt is a few hundred tokens next to executing one, so the top tier is cheap here Which tiers there are, and what they cost, is the unit on the model.

Plan mode

Plan mode is meta-prompting the provider already built for you. In a terminal, press Shift+Tab until the status says Plan, or start a prompt with /plan. In IntelliJ, pick Plan in the agent picker. The agent reads around without changing anything, usually asks about whatever is still open, and hands back a plan. You edit it (in Claude Code, Ctrl+G opens it in your editor), ask for another pass, or approve it. Nothing is carried out before you approve, which makes it a built-in checkpoint on the solution.

You do not always need plan mode. If you already know exactly what to change in 1 file, the decisions are made, and a plan only writes them down for you to approve. Ask for the change directly .

1 ask, not 3

Group changes to the same part of the application into 1 request Every follow-up sends the earlier questions and answers to the model again. That uses extra tokens and increases the cost. Earlier answers and intermediate versions also remain in the context, even when you no longer need them.

Be exact

The less you say, the more the model has to fill in itself. Compare "fix the login" with this ask to the same model: "Make TitleController return a 404 when the catalogue comes back empty. Look at @TitleController.java and @Catalog.java. Do not change Catalog: the problem is how the controller handles an empty result. Done when mvn test is green, with a test for an empty catalogue." That ask names the goal, the files, a limit with its reason and when it is done. With "fix the login" the agent may get there too, but it first has to work out what is wrong and where. That costs more tokens and time, and it can guess wrong.

Say where the job stops, and why. With “Do not throw an exception, because a user that does not exist is a normal outcome”, the reason helps the agent spot related mistakes, such as returning null. Check that it kept to the limit.

Few-shot prompting

Point at code that already does it right. "Do it the way OrderController handles an order that does not exist" hands the agent the structure, the names and the libraries at once It copies an example more faithfully than any description of it. Giving several examples is few-shot prompting, and giving 1 is one-shot prompting.

Output format

Say how you want the answer presented. For a code review, add something like: "List the problems you find, each with the file, the line number and a short explanation" Then you can go straight to each place in the code. For a file, say so: "Write it to review.md." For a fixed shape, pass the template, such as the headings ## Problem, ## Cause and ## Fix, and the agent fills it in instead of choosing its own.

To choose first, ask for options rather than 1 fix: “Give me 3 possible fixes, each with its pros and cons. Do not change anything yet.” Then pick one and have the agent apply it.

Paste the real error

Give the error message, the command you ran and when the error occurs. Paste only the stack trace lines that matter, such as those pointing to your own code If the full output is in a log file, give its path so the agent can search it. Ask it to find and fix the cause.

What no longer works

“Think hard” and “think step by step” are ordinary prompt text, not a setting. Recent models reason on their own: such a phrase at most nudges them to think on that turn, and the reasoning level sets how thoroughly. Claude Code recognises only ultrathink, which asks for deeper reasoning on that one turn. A role such as “senior Java engineer” steers tone and style, not correctness. Concrete requirements, current information and a check give you something to verify.

Capitals and exclamation marks are not needed either: recent models follow instructions closely, and “MUST” or “NEVER” can make the agent apply a rule too rigidly. Keep emphasis for the 1 rule the agent keeps skipping. Otherwise state a rule 1 time, in a normal sentence with a reason: "Use constructor injection so the class is easy to test."
