Everything you send the agent is a prompt. Of everything a model is handed it is usually the smallest, and the session dwarfs it. It is also the most valuable, because it is the one part carrying your intent.

You rarely send just one. Some prompts are fresh queries you type. Others are your answers when the agent asks you about the task .

Instruction

A prompt is an instruction, so say what you want the model to do. Every inaccuracy in it compounds once the agent starts work. Putting one right while it is already working is steering, which comes later.

Not every prompt needs all 5. A one-line fix is a goal and nothing else. The less you fill in, the more the agent decides on its own. The one people leave out is the last: a check the agent can run itself, which step 2's unit on long-running goals and cost takes further.

Reasoning level

The reasoning level guides how thoroughly the model tackles a task. Claude Code’s /effort sets it from low to max on supported models, and Opus 5.5 and Sonnet 5.5 default to medium. In Copilot you set it in the model picker. Higher effort can change reasoning, tool calls and the visible answer It does not select a fixed number of hidden tokens or supply requirements you never gave.

Higher effort can spend more tokens and time. Reasoning tokens are billed as output The chart holds answer length constant to show that cost; real answers and tool use can change too. Use higher effort when the task warrants it, and clarify a vague request first.

That thinking also covers the agent's own moves: which file to open next and what to hand itself as input for the step after that.

Meta-prompting

Meta-prompting is letting a model write the prompt. You say roughly what you want, it writes the instruction, and you read it back and fix the parts it got wrong.

Spend an expensive model on this. Writing a prompt is a few hundred tokens next to executing one, so the top tier is cheap here Which tiers there are, and what they cost, is the unit on the model.

Plan mode

Plan mode is meta-prompting the provider already built for you. Switch to it with Shift+Tab, or start a prompt with /plan. The agent reads around without changing anything, usually asks you about whatever is still open, hands back a plan, and waits. You edit it (in Claude Code, Ctrl+G opens it in your editor), ask for another pass, or approve it. The agent waits for your approval before carrying out the plan.

A reviewed plan turns an underspecified request into clearer requirements. The exercise changes requirements, planning and model choice together. Its scores show which wishes reached the implementation; they do not isolate the effect of plan mode or model size. For that comparison, keep the model and requirements the same.

Plan mode is not always needed. If you already know exactly what needs to change in 1 file, the decisions are made. A plan only puts those decisions in writing for you to approve. Ask the agent to make the change directly .

One ask, not three

Group changes to the same part of the application into 1 request Every follow-up sends the earlier questions and answers to the model again. That uses extra tokens and increases the cost. Earlier answers and intermediate versions also remain in the window, even when you no longer need them.

State exactly what the model should do

"Fix the login" and "make TitleController return a 404 when the catalogue comes back empty" go to the same model. The second names the class and the case. The first leaves the model to guess both.

Say where the job stops and explain why. “Do not throw an exception from UserRepository, because the nightly import expects null” supplies both a constraint and its purpose. The reason helps the agent spot related mistakes, such as changing that return value to an Optional. Verify that it followed the constraint.

Few-shot prompting

Point at code that already does it right. "Do it the way OrderController handles an order that does not exist" hands the agent the structure, the names and the libraries in one go It copies an example more faithfully than any description you could write of it. Giving several examples in the prompt is few-shot prompting. With 1 example, it is called one-shot prompting.

Output format

Specify how you want the answer presented. When you ask the agent to review code, add something like: "List the problems you find. For each problem, include the file, line number and a short explanation" That lets you go straight to the relevant place in the code.

State the action boundary explicitly. “Review only; do not edit files. Give me 3 possible fixes” makes your intent clearer than “suggest a fix”. Then choose an approach and authorise the edit. Use permissions when the boundary must be enforced.

Paste the real error

Share the error message, the command you ran and when the error occurs. Include only the relevant stack trace lines, such as those pointing to your own code If the full output is in a log file, give its path so the agent can search it for the relevant details. Ask the agent to investigate and fix the cause.

What no longer works

Typing “think hard” is ordinary prompt text, not a substitute for Claude Code’s /effort setting. Claude Code recognises only ultrathink, which asks for deeper reasoning on that turn. A role such as “senior Java engineer” can steer style and behaviour, but does not establish correctness. Concrete requirements, current evidence and checks give you something to verify.

Capital letters and exclamation marks are unnecessary too. Recent models already follow instructions closely. Words like "MUST" and "NEVER" can make the agent apply a rule too rigidly, including in situations you did not intend. State the instruction once, in a normal sentence with a reason: "Use constructor injection so the class is easy to test."
