All user input is a prompt. Of everything a model is handed it is usually the smallest. It is also the most valuable, because it is the one part carrying your intent.

You rarely send just one. Some prompts are fresh queries you type. Others come back after the agent interviews you about the task. Every question you answer that way is a prompt too, even when the agent suggested the answers itself.

Instruction

A prompt is an instruction that sets a lot more in motion. It cascades, each step building on the one before. So make sure your prompt actually says what you want the model to do. Any inaccuracy in it only compounds from there.

Models work the question over before they answer. A prompt is seldom enough on its own to carry everything you meant by it. That working over is the reasoning level, and it runs from low up to max. Turn it up and the model reflects on your question rather than answering it straight That absorbs some of the imprecision and the missing information, so what comes back is closer to what you actually meant.

The higher the reasoning, the more tokens the model spends thinking. Those tokens stay in the context and add to the cost So weigh when you need more reasoning, and when you need less.

Worth knowing that the thinking is not only about your question. It also covers the agent's own moves, which file to open next and what to hand itself as input for the step after that.

Meta-prompting

Meta-prompting is letting a model write the prompt. You say roughly what you want, it writes the instruction, and you read it back and fix the parts it got wrong.

Spend an expensive model on this. Writing a prompt is a few hundred tokens next to executing one, so the top tier is cheap here Running the task is where the money goes.

Plan mode

Plan mode is meta-prompting the provider already built for you. The agent interviews you about the task, hands back a plan, and waits. You edit it, ask for another pass, or approve it. No code is written until you do.

A cheaper model driven through a plan routinely beats a one-shot on the expensive one. Most people have that the other way round. The plan turned a vague ask into an exact instruction, and precision was the missing ingredient all along, not model size.

It is not the move every time. A task you have already cut down to one file and one obvious change is a task whose decisions are made, and an interview about it hands them back to you as a document to approve. Ask for it straight instead .

Try it once on something real. Take a task you were about to type as one line, run it through plan mode instead, and read the plan before you approve it. The interview usually surfaces a decision you had not made yet.

Your teacher runs a task through plan mode at the board, so you see the interview and the plan before anything is executed.

What you steer after that

Clear the context when you change subject. The debugging session you just finished is still in the window, and it has nothing to do with the next feature. /clear costs you nothing and hands the whole budget back.

Bundle what you want within one part of the application Every follow-up is another turn, and every turn adds noise the next turn has to read past. That rising disorder is entropy, and it compounds. Three separate questions leave the window messier than one question covering all three.

Be exact about what changes. "Fix the login" and "make ExerciseController return a 400 when the answer is blank" go to the same model. One is specific and lets the model focus. The other makes the model think.
