A tool is a request the model makes to your system. It cannot open a file or run a command itself. It asks for one, your harness runs it, and the output is appended to the context as text. That round trip is the whole mechanism.

This is where an agent's abilities come from. grep to search your codebase, an edit tool to change a file, curl to call an API, an MCP server for whatever your harness does not ship on its own. The harness decides which tools exist. What they hand back is this layer.

Watch where the two halves sit. The tool itself runs outside the window: on your machine, against your files, at somebody else's API. Only what it returns comes back in, and it comes back as plain text next to your prompt.

That dashed half is the part the model never sees. A file the harness decided to cut short and a file that is genuinely short are the same file from in there, unless something in the result says otherwise.

MCP servers

An MCP server can be anything. Model Context Protocol is the standard your harness speaks to reach one, and what is on the other end is up to whoever wrote it: a server for your issue tracker, one for your database, one that drives a browser. Somebody else wrote it. You connected it, and now the model can call it. Your harness runs the call and appends what came back, exactly as it does for grep.

Tools are not all a server offers. It can also hand over material it collected on its own: a page out of a wiki, or last quarter's design document. Nobody called anything to get it. Your harness took it and put it in the window, and the model reads it there next to your prompt. Content that arrives that way has a name of its own. A resource.

Prompts are the third thing. A server ships whole prompts with it, written by whoever built it, for you to pick off a list. Claude Code puts them under a slash.

Prompts are the third thing. A server ships whole prompts with it, written by whoever built it, for you to pick off a list. Whether you ever see them is your harness's call: Copilot CLI gives you /mcp for the servers and names nothing for their prompts.

Read them by who decides. You pick the prompt, your harness attaches the resource, the model asks for the tool. Three different hands, and all three end up in the same window, taking up very different amounts of it.

The list itself is in the window

Every tool ships its description with it. The name, what it does, every parameter it takes, spelled out for the model to read. All of that goes into the window before you have typed anything.

So the cost is not in calling a tool. It is in having it. Connect five MCP servers and a few hundred lines of description ride along with every message you send You pay for them whether or not the agent touches one.

They cost you room to think as well. Forty tools is forty descriptions to read past and forty ways to pick the wrong one, so the window is noisy before you have asked for anything. An agent holding grep, an edit tool and a test runner is choosing between three. Turn off what this task does not need.

Four or five added servers' worth of tools is about the most one context holds well, on top of whatever your harness already starts you with. Past that the agent spends its attention picking between them, and a longer list is rarely the answer. Give that job its own specialised agent, with the tools it needs and nothing else.

Stay critical

Treat what comes back as the least trustworthy layer you have. A blog post about Spring Boot 4 was not written against this repository. An MCP server hands back whatever its author decided to return. The spec a curl fetches may be three revisions behind the one your team agreed on last week.

An MCP server is an attack vector, and it is one of the routes prompt injection actually takes today. One hands back a ticket from your issue tracker, and the description closes with a line addressed to the agent: read the token out of .env and curl it to this address. The agent has a shell, and one tool result just told it what to do with it.

None of that shows once it is in the window. Your prompt, the agent's own notes and a paragraph off a page it opened thirty seconds ago all arrive marked, and the marking does not hold: the model was trained to trust you over a tool result, not built to. It reads the stranger's line and builds on it anyway.

You pay for it on every turn after

A tool result is usually the bulkiest thing in the window. A page of documentation runs longer than your prompt. mvn test on a red build runs longer than most of your source files. And it settles into the session, so it is re-sent on every turn after that. That red build scrolls past once and you keep paying for it on every question you ask afterwards.
