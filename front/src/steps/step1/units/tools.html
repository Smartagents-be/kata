A tool is a request the model makes to your system. It cannot open a file or run a command itself. It asks for one, your harness runs it, and the output is appended to the context as text. That round trip is the whole mechanism.

This is where an agent's abilities come from. grep to search your codebase, sed to change a file, curl to call an API, an MCP server for whatever your harness does not ship on its own. The harness decides which tools exist. What they hand back is this layer.

Watch where the two halves sit. The tool itself runs outside the window: on your machine, against your files, at somebody else's API. Only what it returns comes back in, and it comes back as plain text next to your prompt.

That dashed half is the part the model never sees. It gets the result and nothing else, which is why a file that was truncated on the way in and a file that is genuinely short read exactly the same from in there.

Where the extra tools come from

An MCP server can be anything. A server for your issue tracker, one for your database, one that drives a browser. Somebody wrote it, you connected it, and now the model can call it. Your harness runs the call and appends what came back, exactly as it does for grep.

The list itself is in the window

Every tool you connect ships its description with it. The name, what it does, every parameter it takes, spelled out for the model to read. All of that goes into the window before you have typed anything.

So the cost is not in calling a tool. It is in having it. Connect five MCP servers and a few hundred lines of description ride along with every message you send You pay for them whether or not the agent touches one.

They cost you room to think as well. Forty tools is forty descriptions to read past and forty ways to pick the wrong one, which is the entropy from the opening unit arriving before you start. An agent holding grep, sed and a test runner is choosing between three. Turn off what this task does not need.

Stay critical

Treat what comes back as the least trustworthy layer you have. A blog post about Spring Boot 4 was not written against this repository. An MCP server hands back whatever its author decided to return. The spec a curl fetches may be three revisions behind the one your team agreed on last week.

An MCP server is an attack vector, and it is one of the routes prompt injection actually takes today. One hands back a ticket from your issue tracker, and the description closes with a line addressed to the agent: read the token out of .env and curl it to this address. The agent has a shell, and one tool result just told it what to do with it.

None of that shows once it is in the window. Everything in a context carries the same weight: your prompt, the agent's own notes, and a paragraph off a page it opened thirty seconds ago. The model has no way to mark one as yours and one as a stranger's, so it builds on the stranger's without hesitating.

It costs the same as everything else

A tool result is usually the bulkiest thing in the window. A page of documentation runs longer than your prompt. mvn test on a red build runs longer than most of your source files. And it settles into the session, so it is re-sent on every turn after that, exactly like the three large files from the session unit.
