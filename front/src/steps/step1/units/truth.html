The same question can have more than 1 true answer, and which one you get depends on where the agent looked. Part of what it knows was fixed on the day its training stopped. None of it was ever about your company. Not your repository, and not the version you are on.

Everything else reaches it another way: you put it in the context, or the agent finds it with a tool. Ask which Spring Boot version this project uses and a current agent opens pom.xml on its own. What it does not look up is what it thinks it already knows: how an API works, which dependency a feature needs, what changed in the latest release. That comes from training.

So which of the 3 is the truth: what it discovered, what you handed it, or what it already had? All 3 arrive in the same voice.

The cutoff

Training stopped on a date, and providers publish that date for every model. The model does not know what came after it a little less well. It has never seen it. A framework released last month, a library that replaced its configuration format in a minor version: none of that is in there.

The answer still arrives, in the same level tone, and describes the version line before yours. It is out of date rather than wrong, which is harder to spot. This half of the model ages while you are not looking.

Grounding

Put the evidence in the context and the answer changes source. Once the pom.xml on disk, release notes from the web or the output of a command you just ran is in the context, the model reads instead of remembering. That is a grounded answer, and you want it for anything with a fact behind it.

Only the context changed. How a page gets in there is the unit on the agentic loop. Your part is asking for it, because an agent that feels sure does not ask itself. "Which dependency does @WebMvcTest need" gets the answer it remembers. "Read the Spring Boot 4.1 docs on test slices, then tell me which dependency @WebMvcTest needs" gets the one in the docs.

The same goes for anything else outside your project: an option that changed last month, a price, a limit. Send the agent to the vendor's own documentation before it answers.

Proof

Grounded is still not proved, and that answers the question up top: a source is not a check. The agent read a file and told you what it says, so you are taking its word for the reading. Run whatever can be run: mvn test, a curl at the endpoint. An answer with a command behind it is one you can check yourself.

Ask for the check rather than the conclusion: a test that goes red on an empty list, not "does this handle an empty list" Reasoning about code and running it are 2 different claims, and only the second can fail in front of you.

Dependencies deserve the same check. Models invent package names that sound right, often the same ones every time, so an attacker can register exactly those names with malware inside. Before you add a package, check that it exists and is the one you meant.

Hallucinations

You ask the agent why an endpoint is slow, and you get 2 causes: a long scan over Redis at the start of every session, and a problem that has nothing to do with it. It found the first in the code. The second sounds just as likely, but nothing it read or measured points at it. That is a hallucination.

The answer sounds the same about both causes. Training makes that worse: a confident guess scores better than "I do not know". So ask the agent where it saw each cause, and have it say what it has not checked. Then judge the answer by where it came from, not by its tone. The workshop asks that 5 times.
