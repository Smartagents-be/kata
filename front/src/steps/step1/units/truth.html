The same question can have more than one true answer, and which one you get depends on where the agent looked. Part of what it knows was fixed on the day its training stopped. None of it was ever about your company. Not your repository, and not the version you are on.

Everything else has to reach it somehow. You put it in the window yourself, or you send it to find out with a tool. Ask which version of Spring Boot this project builds on and you probably get the version most projects were on when it was trained, because nothing sent it to look. Tell it to read pom.xml first and the number is in the window before the answer is.

So which of the three is the truth? The one it went and discovered, the one you handed it, or the one it already had. All three arrive in the same voice.

The cutoff

Training stopped on a date. Whatever was published after it is not something the model knows a little less well. It has never seen it. A framework released last spring, a library that threw out its whole configuration format between one minor version and the next: none of that is in there.

The answer still arrives. It describes the version line before yours, in the same level tone as everything else. It is out of date rather than wrong, and that is harder to spot. This is the half of the model that ages while you are not looking.

Grounding

Put the evidence in the window and the answer changes source. The pom.xml on disk, the release notes fetched off the web, the output of a command that ran a second ago: once any of it is in the context, the model is reading rather than remembering. That is a grounded answer, and it is the one you want for anything with a fact behind it.

Only the window changed. How the file gets in there is the unit on tools. Your part is asking for it. "Which version does this project use" invites a guess. "Read pom.xml and tell me which version this project uses" does not.

For anything outside your project, the evidence is the official documentation. A library's current API, an option that changed last month, a price: ask the agent to search for the vendor's own docs and read them before it answers. Then the page is in the window and the answer comes from it, rather than from whatever version the model was trained on.

Proof

Grounded is still not proved, and that is the answer to the question up top: the source is not the same thing as the check. The agent read a file and told you what it says, and you are taking its word for the reading. Run whatever can be run: mvn test, a curl at the endpoint, one line of jshell. An answer with a command behind it is one you can check yourself.

Ask for the check rather than the conclusion, then. Not "does this handle an empty list" but a test that goes red on an empty list Reasoning about what the code does and running it are two different claims, and only one of them can fail in front of you.

Hallucinations

With nothing in the window to read, the model answers anyway. Answering is what it does, and you have met it once already: the quiz back in the context unit asked why a confident answer about a UserService missed the class entirely. Ask which method on Catalog filters titles by author and you get findAllByAuthorOrdered, spelled exactly the way a Spring method is spelled, on a class that has no such method. Nothing was looked up, and nothing was deliberately made up. The next likely token landed where a fact should have been, and that is a hallucination.

Two of those were read and one was not, and the answer says the same thing about all three. A hallucination is expensive because the model sounds the same whether it read your file or filled the gap. Stop reading the tone and start asking where the answer came from. The workshop is that question five times over.
