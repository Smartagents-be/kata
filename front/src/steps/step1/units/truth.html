The same question can have more than one true answer, and which one you get depends on where the agent looked. Part of what it knows was fixed on the day its training stopped. None of it was ever about your company. Not your repository, not your conventions, not the version you are actually on.

Everything else has to reach it somehow. You put it in the window yourself, or you send it to find out with a tool. Ask which version of Spring Boot this project builds on and you might get the version most projects were on when it was trained, because nothing sent it to look. Tell it to read pom.xml first and the number is in the window before the answer is.

So which of the three is the truth? The one it went and discovered, the one you handed it, or the one it already had. All three arrive in the same voice.

The cutoff

Training stopped on a date. Whatever was published after it is not something the model knows less well, it is something the model has never seen. A framework released last spring, the API your team deprecated in March, the library that threw out its whole configuration format: none of that is in there.

The answer still arrives. It describes the version before yours, in the same level tone as everything else, and it is out of date rather than wrong, which is the harder thing to spot. This is the half of the model that ages while you are not looking.

Grounding

Put the thing in the window and the answer changes source. The pom.xml on disk, the release notes fetched off the web, the output of a command that ran a second ago: once any of it is in the context, the model is reading rather than remembering. That is a grounded answer, and it is the one you want for anything with a fact behind it.

Only the window changed. Getting the file in there is the unit on tools, and what is on you is asking for it. "Which version does this project use" invites a guess. "Read pom.xml and tell me which version this project uses" does not.

Proof

Grounded is still not proved. The agent read a file and told you what it says, and you are taking its word for the reading. Anything that can be run should be run: mvn test, a curl at the endpoint, one line of jshell. An answer with a command behind it is a different kind of answer.

Ask for the check rather than the conclusion, then. Not "does this handle an empty list" but a test that goes red on an empty list Reasoning about what the code does and running it are two different claims, and only one of them can fail in front of you.

Hallucinations

With nothing in the window to read, the model answers anyway. Answering is what it does. Ask which method on Catalog filters titles by author and you get findAllByAuthorOrdered, spelled the way the rest of that class spells things, on a class that has no such method. Nothing was looked up and nothing was invented on purpose. The next likely token landed where a fact should have been, and that is a hallucination.

Two of those were read and one was not, and the answer says the same thing about all three. That is what makes it expensive. No wobble in the tone, no hedge, no shorter sentence, because the model sounds the same whether it read your file or filled the gap. Stop reading the tone and start asking where the answer came from.
