The harness is the software you use to work with a model. Claude Code or Copilot in your terminal, Cursor, the chat in your IDE. You type a question, the harness turns it into a request and sends it off to the provider.

Into that request it loads its own material: skills, tool definitions, system prompts, guardrails. You wrote none of it and mostly never see it. That is why an agent already knows it can open a file or run a command without you ever mentioning it.

Which harness you run

Everything the model ever learns about your work, it learns because the harness put it in the request: it reads your files, drives your terminal and holds the connection to your provider's API.

Each provider ships its own harness around its own models, and there are open-source ones you point at whichever model you want. They do not start you in the same place. Copilot CLI arrives with the GitHub MCP server already connected, so those tool definitions are in every request from the first turn. Claude Code starts with none until you add one.

Caching

Re-sending the whole window every turn would be ruinous at full price, and you do not pay full price The harness puts a mark in the request, and on the next turn everything up to that mark is recognised and billed at roughly a tenth.

What gets matched is a prefix, read from the first byte, so anything that changes early makes everything behind it new again. Connect an MCP server halfway through a session and the tool definitions at the top shift, so the whole window is priced from scratch. Switch models and the cache does not come with you. Let compaction rewrite the pile and there is nothing left to match.

An entry goes stale after about five minutes by default, and you can pay for longer. It is worth real money to keep one alive Walk away for a meeting and you come back to a window priced from scratch, so picking up where you left off costs you the whole thing again. Start a fresh session instead.

How a harness splits the work

Your task does not have to go to one model in one conversation. Harnesses have a few ways of cutting it up, and each one is a design pattern worth recognising, because it decides where your context ends up.

Decomposition

Whatever you ask for is thinner than what you want. "Add search to the catalogue" does not say what an empty query returns, whether it matches on title only, or what comes back when nothing matches. That is not an agent problem. Requirements have arrived under-specified since long before any of this, and most of traditional software engineering is spent closing that gap. A task has no depth until somebody gives it some.

Decomposition is the harness cutting the task into parts that stand on their own, before it builds any of them. Each part gets its own prompt, and a prompt has to say what that part does. Vague does not survive the exercise. You cannot write "handle the empty case" as an instruction without first deciding what handling it means.

So the questions come back at you before the code does. Cutting is where the hidden requirements surface: the case nobody thought about, the endpoint two parts both want to own, the decision that was never made. An agent that starts typing instead would have guessed at every one of them, and you find guesses in the diff.

The coordinator

One model runs the job and hands pieces of it out. That one is usually the stronger and more expensive model, and the pieces go to smaller, cheaper models (sub-agents). You pay the top rate for working out what to do and a fraction of it for doing it Carrying the work out usually costs more than working out what to do, so that is where the saving sits.

A sub-agent starts on a fresh session with an empty context. The coordinator writes one base instruction and hands it to that new context, and it is all the sub-agent gets. So a sub-agent is probably missing a lot, and whatever it misses it has to fetch for itself: open the source files and read them again. That is tokens and time, which is where this pattern gets expensive.

The coordinator decomposes first, for that reason. Every part it hands out is a prompt written into an empty context, so cutting well is most of the work here. It is the same skill as writing a good prompt yourself.

The sequential workflow

Nothing is handed out here. The agent plans the steps first, then works through them one at a time, and every step is validated before the next one starts. This gives you the option to stop, and pick it back up later.

Reach for this when the steps depend on each other. What it costs you is the window: one session carries the whole run, so a long workflow is a full context by the end of it.

Reflection

Reflection is the agent putting a critic on its own work. The sub-agent is told to attack the result rather than help with it: find what is wrong, say so, report back. The shape is the same as a GAN's, where one network produces something and another one tries to tear it down.

The empty context is what makes it work. An agent reviewing its own transcript has spent the last hour arguing for this design and will agree with itself. A critic that arrives with nothing but the code has no such stake, so what it hands back is worth reading.
