The harness is the software you use to work with a model. Claude Code or Copilot in your terminal, Cursor, the chat in your IDE. You type a question, the harness turns it into a request and sends it off to the provider.

Into that request it loads its own material: skill descriptions, tool definitions, system prompts, guardrails. You wrote none of it and mostly never see it. That is why an agent already knows it can open a file or run a command without you ever mentioning it.

The harness reads your files, drives your terminal and holds the connection to your provider's API. Everything the model ever learns about your work, it learns because the harness put it in the request.

Which harness you run

Harnesses differ in defaults and providers. Claude Code and Copilot CLI mostly load a tool’s definition only when it is needed, but the exact rule depends on the harness and the model.

Caching

Prompt caching reuses the start of a request that matches an earlier one On Anthropic’s API, a cache write costs 1.25 times input for a 5-minute cache or 2 times for a 1-hour one, and a cache read 0.1 times input or less, depending on the model. Copilot bills it too.

The cache only matches from the start, and each model has its own. So pick your model, effort and tools before you begin.

A cache lives 5 minutes or 1 hour, depending on your harness and account. Its usage report shows which.

How a harness splits the work

Your task does not have to go to 1 model in 1 conversation. How a harness cuts it up decides where your context ends up.

Decomposition

Whatever you ask for is thinner than what you want. "Add search to the catalogue" does not say what an empty query returns, whether it matches on title only, or what comes back when nothing matches. That is not an agent problem. Requirements arrived under-specified long before there were agents, and most of traditional software engineering is spent closing that gap. A task has no depth until somebody gives it some.

Decomposition cuts a task into parts that can be checked separately. Each brief names the outcome, relevant context and dependencies. Writing “handle the empty case” forces you to decide what that means before delegating it.

So the questions come back at you before the code does. The case nobody thought about, the endpoint 2 parts both want to own, the decision that was never made. An agent that starts typing instead would have guessed at every one of them, and you find guesses in the diff.

The coordinator

A coordinator hands parts of a task to sub-agents, ideally on a cheaper model Splitting multiplies tokens though: Anthropic measured its multi-agent research system at about 15 times the tokens of a chat. Some built-in sub-agents already run on a small model, such as Claude Code's Explore and Copilot CLI's explore and task agents, while sub-agents in IntelliJ use your main model. Check which model a worker runs on.

A sub-agent often starts without your instructions file, so put the rules that matter in its brief. A fork starts from a copy of your conversation.

The coordinator decomposes first, for that reason, and cutting well is most of the work. It is the same skill as writing a good prompt yourself.

The sequential workflow

Nothing is handed out here. The agent plans the steps first, then works through them one at a time, and every step is validated before the next one starts. You can stop between any 2 steps and pick it up later.

Reach for this when the steps depend on each other. It costs you the window: 1 session carries the whole run, so a long workflow ends on a full context.

Reflection

Reflection is the agent putting a critic on its own work. The critic is a sub-agent, told to attack the result rather than help with it: find what is wrong and report it.

A critic with its own brief is less tied to the builder’s choices. Still check each finding before you act on it.
