This step named the layers an agent's context comes from: the prompt, the session, the harness and the tools it can reach. Each one arrives from a different place and lands in the same window. Now you go the other way. You find what a layer is holding when the thing holding it does not want to show you.

The step 1 backend is your target. It has one endpoint, GET /api/titles, and the Catalog page in the sidebar calls it. Nine book titles come back. The pipeline behind them computes more than nine lines on every request and throws most of them away before you ever see them. Three of the thrown-away lines are flags, each wrapped in {curly braces} and written in leetspeak so you cannot mistake one for a title.

You have an agent. Use it. This is where you find out what it reaches on its own and what it can only reach because you put something in front of it.

Do not expect one prompt to do it. Ask an agent to find the flags in this repo and it comes back fast, confident and wrong. Forty-one stages restore a string, eleven of them comment out the line that would publish it, and five of those eleven are flags in exactly the same shape. Nothing in the code says which. Searching the source is cheap and it puts the source in the window. It does not put the run in the window, and it does not put your judgement there either. That is this whole step aimed back at you.

Start the backend, then work the three sections below. They line up one for one with the three rows on the board. 

mvn spring-boot:run
curl -s localhost:8080/api/titles | jq

Read the source

One flag sits in the code and never executes. Somewhere in the services package a line restores a string inside a branch nothing can reach. Run the service all day and it never fires, so no trace will ever print it. Reading is the only way in.

This is the layer your agent is best at, and your whole job is aiming it. Give it the services package and ask for a branch whose condition cannot be true. To turn the literal into text it also needs Scramble open, so say so, or watch whether it goes and gets the file itself. Two files in the window and the answer is there.

One thing to insist on: make it run the decode rather than reason about it. An agent doing character arithmetic in prose will hand you a plausible string with two letters wrong, and it will sound just as sure as if it were right. A throwaway main or a line of jshell settles it. That is the difference between an agent that answers and an agent that checks.

What you have used here is tools context: the code on disk, read back as written. It is in the window because a tool went and got it, and nothing else was needed.

Trace the run

The second flag is computed while the pipeline runs and dropped before the response is built. No amount of reading settles this one, so an agent staring at the source cannot settle it either. It has to make the pipeline talk. There is one place every restored string passes through: put a log line there, start the service, call the endpoint, read what comes back, then take the line out again.

Notice what that costs. The agent edits a file, runs a command and reads the output, and all of it lands in the transcript as tool results. That is your session filling up with what happened this time round. It is the only layer that knows anything about this run, and it did not exist until something was executed.

Then the part you cannot hand over. Five {leetspoken} lines come out of that trace and only one is the flag. They are the same shape and the same length band, and the code gives away nothing about which is which. The difference is what they say. One of them is about the thing you just did to find it. Your agent has no way to pick. You do.

Turn up the logs

The third flag is not readable in the source and not present in a normal run. It prints only when the log level is high enough. Start the service with debug logging on, call the endpoint again, and read the console. 

mvn spring-boot:run -Dspring-boot.run.arguments=--logging.level.be.smartagents.kata.java.step1=DEBUG

Same code, same request, more output. A setting neither you nor the agent wrote decided what was visible, and until you changed it neither of you could see past it. That is harness context. Your agent sits inside one all day: a system prompt it did not choose and a set of tools it was handed, deciding what it can see and do before you type anything.

The board

Each flag goes in its box below. The board checks it here in the browser against a hash, so this half grades with the backend down. It never tells you the answer. It only confirms you read what the pipeline was hiding.

When all three are in, look back at how you got them. One you could hand over whole. One needed you to decide. Knowing which is which, before you start, is most of working well with an agent.

Stuck?

For the first, look for a stage that folds a value into a small range and then compares it against a bound it can never cross. The line inside that branch is the one you decode.

For the second, the instrument that works is a single log line in Scramble.unveil. Every restored string goes through it, including the ones that are never published. Logging CatalogRun.publish instead will miss the flag, because the stage holding it never calls publish.

Your teacher will run all three live: the branch that cannot fire, a trace of one request, and the same request again with debug on, so you can watch one pipeline give up three different things.
