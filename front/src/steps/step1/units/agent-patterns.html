Your task does not have to go to 1 model in 1 conversation. How it is cut up decides where your context ends up.

Decomposition

Whatever you ask for is thinner than what you want. "Add search to the catalogue" does not say what an empty query returns, whether it matches on title only, or what comes back when nothing matches. That is not an agent problem. Requirements arrived under-specified long before there were agents, and most of traditional software engineering is spent closing that gap. A task has no depth until somebody gives it some.

Decomposition cuts a task into subtasks, and those again where needed, until every piece is small enough to carry out in a single pass. An agent can write a plan and work through it task by task itself: that is the sequential workflow further down. Or it hands every piece to a sub-agent, as in the figure: the coordinator below, but over several levels. Every result goes back to whoever handed the piece out.

In Claude Code a sub-agent can cut its piece again for sub-agents of its own. In Copilot in IntelliJ a sub-agent cannot start sub-agents, so the main agent does all the cutting itself.

Every level adds model calls, so more time and more tokens. Use it for a large, vague task, not for a change you can describe in 1 sentence.

The coordinator

A coordinator hands parts of a task to sub-agents, ideally on a cheaper model Splitting multiplies tokens though: Anthropic measured its multi-agent research system at about 15 times the tokens of a chat. Copilot CLI's built-in explore and task agents already run on a small model. Claude Code's Explore and sub-agents in IntelliJ use your main model, so check which model a worker runs on.

A sub-agent does not see your conversation, so put the decisions that matter in its brief. Some also skip your CLAUDE.md or AGENTS.md, such as Explore and Plan in Claude Code, and explore, task and code-review in Copilot CLI. A fork starts from a copy of your conversation.

The coordinator decomposes first, for that reason, and cutting well is most of the work. It is the same skill as writing a good prompt yourself.

The sequential workflow

Nothing is handed out here. The agent writes a plan with tasks into a file, then works through them one at a time and tests each before it starts the next.

Reach for this when the tasks depend on each other. It costs context: 1 session carries everything the agent did, so a long run fills up. Because the plan is a file, you can stop between 2 tasks and carry on in a fresh session that reads the plan.

Reflection

Reflection is the agent putting a critic on its own work. The critic is a sub-agent told to find what is wrong with the result and report it, not to help.

A critic with its own brief is less tied to the builder’s choices. Still check each finding before you act on it.

Routing

Routing sorts a request and sends it to the handler that fits: a model, a skill or a sub-agent. Your harness already does it. A custom agent is 1 Markdown file with a description, its allowed tools and its instructions, in .claude/agents/ for Claude Code or .github/agents/ for Copilot. The harness picks a skill or custom agent by its description, so that description decides whether it ever gets used.

The sorting needs no model that writes text. Jev, from TypeSafe AI, is a decision model (TypeSafe calls it a System One model) that answers with a choice and a probability. A community project, jev-model-router, uses it to pick the Claude model for each turn in Claude Code, and plain code checks each answer before the model is switched.
