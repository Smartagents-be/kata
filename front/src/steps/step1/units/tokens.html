Before anything reaches the model, your text is cut into chunks and every chunk is swapped for a number. Those chunks are tokens.

Text reaches a language model as tokens. They measure how much text fits and how much is processed. A token count is not a word count or a character count. Images become tokens too, and are billed the same way. Claude counts roughly (width ÷ 28) × (height ÷ 28): 1 token per block of 28 by 28 pixels. A screenshot of 1000 by 1000 pixels is about 1,300 tokens. A larger image is scaled down first, so on current models 1 image costs at most about 4,800 tokens.

A token is usually a few characters, rather than a whole word. The exact split depends on the model and the language. For context limits and cost estimates, use the token count your tool reports.

Reading

Models do not process text as separate words

A tokeniser uses a fixed vocabulary and segmentation rules learned from text. Common words often stay whole; other words split into smaller pieces. Different tokenisers draw different boundaries, even between versions of the same model: Claude Opus 4.7 cuts the same text into up to 35% more tokens than Opus 4.6.

In these examples, text and Java code use similar numbers of tokens per character. A log line uses nearly 2 times as many, an id nearly 3 times. Those ratios depend on the text and the tokeniser. Long logs full of ids can fill the context quickly.

The sentence above uses 10 tokens in English and 12 in Dutch with this tokeniser. Most languages need more tokens than English for the same content. A tokeniser learns its pieces mostly from English text, so English words stay whole more often. Other languages cost more and fill the context sooner. That says nothing about the quality of the answers.

Attention

In He deposits his money at the bank, bank could mean a river bank or an institution that handles money. The words deposits and money help identify the right meaning. The model weighs information from other tokens to make such connections. That weighing is called attention.

In every attention step, the model computes 3 vectors for each token: a query, a key and a value. They serve different roles. When a token seeks information from other tokens, its query expresses what it needs. When other tokens attend to this token, its key expresses what it offers. Its value contains the information it actually contributes.

For bank, the model compares its query with the keys of every earlier token and itself. It calculates their dot product: multiply the numbers at corresponding positions in the 2 vectors, then add the results. Each comparison produces a score.

The scores are converted into weights that add up to 100%. The higher the score, the more the corresponding value contributes. The model multiplies each value-vector by its weight and adds the vectors together, position by position. That lets information from deposits and money weigh heavily in understanding bank.

During training, the model learns how to calculate these vectors to make useful connections. When it writes, it uses those learned calculations.

That step happens many times side by side, and again in every layer, each time with new vectors. This drawing shows 1 run with invented weights and omits attention to the token itself. It has 21 pairs for 7 tokens and 91 for 14.

Writing

The model generates 1 token at a time

The model gives every token in its vocabulary a score, based on the context so far, and 1 token is picked. That token goes on the end of the text, and the next prediction starts from that longer sequence. A token depends only on what comes before it, so adding one changes nothing that was already calculated. The model reuses those calculations from a cache instead of working through the whole text again. That also works across requests: when a request starts with the same text as an earlier one, that start can be reused, at a lower rate That is prompt caching, and its rates close this unit.

After it alone, almost anything can follow, such as is or was. After the build failed because it, timed becomes the favourite. Everything you leave in front of a model changes what comes out of it, whether you meant it to or not.

The favourite is not always what comes out. Those scores are probabilities, and the model picks one according to them, so ask the same question 2 times and you can get 2 different answers. None of the other words above was impossible. They were only less likely.

You do not set any of these yourself: Claude Code and Copilot choose them for you, and the newest Claude models accept only the defaults.

The real cost

Output is priced above input in the table in the model unit. The model reads the whole input at once, but writes the answer 1 token at a time, with a separate pass for each token.

Thinking is writing too. Reasoning is billed as output, including the reasoning you never see: what reaches your screen is at most a summary, and the bill is for the whole thing. Here is 1 turn deep in a session, with the reading and the writing side by side.

Prompt caching

On Anthropic’s API, a cache write costs 1.25 times input for a 5-minute cache or 2 times for a 1-hour one. A cache read costs 0.1 times input or less, depending on the model. Copilot bills it too. Your harness and account decide which lifetime you get, and the usage report shows it.

The cache only matches from the start, and each model has its own. So pick your model, effort and tools before you begin.
