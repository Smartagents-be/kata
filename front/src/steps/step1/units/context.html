Each turn, the harness sends the model 1 request. Everything in it is the context.

A model is stateless

The model remembers nothing between requests: each time, the harness sends the whole conversation again. A new session starts without that conversation, but with the files the harness reads in at the start.

Claude Code calls those files memory. You write CLAUDE.md. Claude also keeps its own notes per project and loads the first 200 lines of them. Type /memory to see both. So memory is not something the model remembers: it is text that comes back into the context every session.

Copilot works the same way. You write .github/copilot-instructions.md. With Copilot Memory, still in preview, Copilot also stores facts about a repository itself, and deletes a fact it has not used for 28 days. So memory is not something the model remembers: it is text that is handed to it again.

Sending the whole transcript again costs focus as well as money. Clear the session often, and always when you switch to something unrelated A fresh session keeps the model focused, even when it has to re-read a file to solve the problem in front of it.

Context makes the task specific

The model predicts from what it learned and what is in the context. Without the current code, the failing case and your conventions, it has little to go on. You get an answer that could fit any project, but not necessarily yours.

Below you can see how much 1 piece of context changes. Both pages come from the same prompt: a landing page for a book rental. On the left the model got only that prompt, on the right also 1 reference image from Dribbble.

That 1 image steered the design away from the generic straight away. It is not finished, but it is closer to what you want.

Your codebase is that reference. Every file the agent opens on the way to your change is context too, and it steers the answer the same way that image did. Keep one way of doing things and the agent copies it. Work in a project that drifted years ago and it copies that instead, every turn and every session. That is why an old codebase feels heavy.

Bad context, bad answers

Missing context produces generic output. You recognise it instantly: the tutorial answer, the UserServiceImpl, the try-catch that swallows the exception. It is not wrong exactly. It answers a question nobody in your team asked.

Often that gap is recoverable, because the harness can go and get what it lacks. When reading is not enough, it interviews you instead.

Wrong context can mislead the model even when its source is labelled. Paste a file that is 3 versions old and the agent can build on a stale assumption. Have it inspect the current file and compare dates or versions when freshness matters.

And it slips in by accident more than you would think. Chase a bug through a long session and finally kill it. The fix lands in your code, but the whole hunt stays in the context. The broken version, the wrong turns, the diff you reverted, all still sitting there. Ask for the next thing without clearing and the model reads that dead code as live. It can decide your fix was the mistake, put the bug back, and the first you hear of it is the test going red again That pile-up in the context is entropy.

Why this bites hardest in code

Training material includes code of uneven quality: tutorials, old answers and snippets never tested in your environment. A plausible function can compile while breaking your domain rules. Give the agent your current conventions and executable checks.

Training can teach useful coding practices, but it does not establish what your team chose in 2019. A vague request leaves those choices open. Point at a current implementation and state what must hold, then verify the result.

More context is not free

Everything in the context is sent again with every message. The cache makes that cheaper, not free.

So the goal is not maximum context. It is context that is small enough and good enough. The file that matters instead of the whole directory.

You choose most of it

Name the class and the case, as the prompt unit asks. Paste the failing assertion and relevant stack trace lines Point at a class that follows your conventions, so the agent has a concrete reference.

When you do not know where a change belongs, ask the agent to locate it and report before editing. Starting in exercises/step1/java focuses discovery on that project. The working directory is also the default boundary: the agent asks before it reads or edits files outside it. That is a permission prompt, not a sandbox.

Entropy

A long session piles up failed attempts, errors and old versions of files. The harness does not reliably clear them out.

That is entropy: disorder in the context rises with every turn unless somebody spends energy pushing it back down. You see it when the agent starts contradicting itself, re-proposes an idea you already rejected, or edits a file back to a version you moved past an hour ago.

Even relevant material can be missed in a long context. Some models and tasks show weaker retrieval for information placed in the middle. That is called lost in the middle. More broadly, answers get less reliable as the input grows, even when the task stays just as easy. Researchers call that context rot. Keep critical constraints easy to find and check whether the result follows them.

Amnesia and context fatigue

Because the context is finite, something eventually has to give. Older material is summarised, and the summary is what stays. The constraint you gave at the start is now 1 line in it, or it did not make the cut at all.

Then the agent forgets a decision from earlier, asks a question you already answered, or re-reads a file it read 20 minutes ago. This is context fatigue. The model did not get tired and it did not get dumber. The evidence left the room.

When the context is compacted, detail is the first thing to go. For an instruction that has to survive that, write it in CLAUDE.md, which is read at the start of every session and again after compaction. And keep the context from filling up in the first place: cut each task small enough that it finishes before the summarising begins.
