Each turn, the harness sends the model 1 request. Everything in it is the context.

A model is stateless

The model remembers nothing between requests: each time, the harness sends the whole conversation again. A new session starts without that conversation, but with the files the harness reads in at the start.

Claude Code calls those files memory. You write CLAUDE.md. Claude also keeps its own notes per project and loads the first 200 lines of them. Type /memory to see both. So memory is not something the model remembers: it is text that comes back into the context every session.

Copilot works the same way. You write AGENTS.md. With Copilot Memory, still in preview, Copilot also stores facts about a repository itself, and deletes a fact it has not used for 28 days. So memory is not something the model remembers: it is text that is handed to it again.

Context makes the task specific

The model predicts from what it learned and what is in the context. It was trained on code from a great many projects. Without the current code, the failing case and your conventions, it falls back on what is common across them: an answer that could fit any project, but not necessarily yours.

Below you can see how much 1 piece of context changes. Both pages come from the same prompt: a landing page for a book rental. On the left the model got only that prompt, on the right also 1 screenshot of an existing design as an example.

On the left you see the default choices that keep coming back in AI-made designs: everything centred, a large serif headline, a little pill with a dot above it and the same rounded corners everywhere. That 1 example on the right steered the design somewhere else straight away. It is not finished, but it is closer to what you want.

Your codebase is that example. Every file the agent reads steers the answer the way that image did. Claude Code's system prompt even tells it, in so many words, to write code that reads like the surrounding code. Do things one way consistently and the agent copies that. Let a project drift for years and it copies the drift.

Bad context, bad answers

Missing context produces generic output: code that could sit in any project. A UserService interface with a UserServiceImpl beside it, because that is what the tutorials do. A try-catch that logs the exception and carries on. It compiles, but it can break your domain rules. It answers a question nobody in your team asked.

Often that gap can be closed, because the agent can use its tools to fetch what it lacks: read files, search your codebase, run the tests or git log, or pull documentation from the web. When that is not enough, it interviews you It is not guaranteed to do either.

Wrong context can mislead the model. A realistic case: your CLAUDE.md or AGENTS.md still says new endpoints go in a web package, while the team has long given every feature its own package. The agent follows the file, and nothing in the code stops it. So put a line in that file that has the agent propose an edit to it whenever you say something that contradicts it. You approve, and the file stays current When in doubt, also have the agent read the existing code.

More context is not free

Everything in the context is sent again with every message. The cache makes that cheaper, not free.

So the goal is not maximum context. It is context that is small enough and good enough. The file that matters instead of the whole directory.

Even relevant material can be missed in a long context. Some models and tasks show weaker retrieval for information placed in the middle. That is called lost in the middle. More broadly, answers get less reliable as the input grows, even when the task stays just as easy. Researchers call that context rot. Keep critical constraints easy to find and check whether the result follows them.

What you give the agent

Per task, give what holds for that task only: the class and the scenario, as in the prompt unit, and the failing assertion with the relevant stack trace lines Also point at a class that follows your conventions, so the agent has a concrete reference.

When you do not know where a change belongs, ask the agent to locate it and report before editing. Starting in exercises/step1/java focuses discovery on that project. The working directory is also the default boundary: the agent asks before it reads or edits files outside it. That is a permission prompt, not a sandbox.

What holds for every task does not belong in your prompt but in the project: in your CLAUDE.md or AGENTS.md, in rules per part of the codebase, and in gates that fail when it goes wrong. Only a gate is certain. Whether the agent keeps to your DDD rules you otherwise only find out by reading the code yourself. So write rules like that down as architecture tests that fail when a class breaks them. How to set that up is in step 2.

What leaves your machine

Everything in the context goes to the provider: your prompt, the files the agent reads, the output of every command it runs. A log you paste with an API key in it. A stack trace with a customer's email address. A .env the agent opens on its own. Strip secrets and personal data before you paste How to keep a file like .env away from the agent is in step 2.
