Every call the harness makes to the model is 1 request. Everything in it is the context.

A model is stateless

The model remembers nothing between requests: each time, the harness sends the whole conversation again. A new session starts without that conversation, but with the files the harness reads in at the start.

Claude Code calls those files memory: the CLAUDE.md you write, and the notes Claude keeps per project, of which it loads the first 200 lines or 25 KB. /memory shows both. So memory is not something the model remembers: it is text that comes back into the context every session.

Copilot works the same way: you write AGENTS.md, and with Copilot Memory (still in preview, in Copilot CLI and on GitHub) Copilot stores facts about a repository itself, deleting any it has not used for 28 days. So memory is not something the model remembers: it is text handed to it again.

Context makes the task specific

The model predicts from its training, code from a great many projects, and from what is in the context. Without the current code, the failing case and your conventions, it falls back on what those projects have in common: an answer that could fit any project, not necessarily yours.

Below you see what 1 piece of context changes. Both pages come from the same prompt: a landing page for a book rental. The left one got only that prompt, the right one also 1 screenshot of an existing design as an example.

The left one shows defaults that keep coming back in AI-made designs: everything centred, a large serif headline, a little pill with a dot above it, the same rounded corners everywhere. The 1 example on the right steered the design elsewhere at once. Not finished, but closer to what you want.

Your codebase is that example: every file the agent reads steers the answer the way that image did. Claude Code's system prompt explicitly tells it to write code that reads like the surrounding code. Work one way consistently and the agent copies it. Let a project drift for years and it copies the drift.

Bad context, bad answers

Missing context produces generic code. A UserService interface with a UserServiceImpl beside it, because the tutorials do that. A try-catch that logs the exception and carries on. It compiles, but it can break your domain rules: it answers a question nobody in your team asked.

The agent can often close that gap with its tools: read files, search your codebase, run the tests or git log, pull documentation from the web. If that is not enough, it interviews you Neither is guaranteed.

Wrong context can mislead the model. Say your CLAUDE.md or AGENTS.md still says new endpoints go in a web package, while the team has long given every feature its own package. The agent follows the file, and nothing in the code stops it. So add a line to that file: whenever you contradict it, the agent proposes an edit to the file. You approve, and the file stays current When in doubt, also have the agent read the existing code.

More context is not free

Everything in the context is sent again with every message. The cache makes that cheaper, not free. So aim for small and good enough, not maximum: the file that matters, not the whole directory.

A long context can hide even relevant material. Some models, on some tasks, find information in the middle less reliably: lost in the middle. More broadly, answers get less reliable as the input grows, even when the task stays as easy. Researchers call that context rot. Keep critical constraints easy to find, and check the result follows them.

That drop starts long before the context is full. People who work with agents every day put it somewhere around 100K to 150K tokens, as a rule of thumb rather than a measured line. A larger context mostly adds room past that point.

What you give the agent

Per task, give what holds for that task only: the class and the scenario (see the prompt unit), and the failing assertion with the relevant stack trace lines Also point at a class that follows your conventions, as a concrete reference.

If you do not know where a change belongs, have the agent find the place and report before it edits. Starting in exercises/step1/java focuses its search on that project. That folder is also the default boundary: the agent asks before it first reads outside it. A permission prompt, not a sandbox.

What holds for every task belongs in the project, not your prompt: in your CLAUDE.md or AGENTS.md, in rules per part of the codebase, and in gates that fail when it goes wrong. Only a gate is certain. Without one, you only learn whether the agent kept to your DDD rules by reading the code yourself. So write such rules as architecture tests that fail when a class breaks them. Step 2 shows how.

What leaves your machine

Everything in the context goes to the provider: your prompt, the files the agent reads, the output of every command it runs. A log you paste with an API key in it. A stack trace with a customer's email address. A .env the agent opens on its own. Strip secrets and personal data before you paste How to keep a file like .env away from the agent is in step 2.
