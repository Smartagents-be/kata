The people around you saw what you saw. A working version of something, on screen, an afternoon after somebody asked for it. What they took away is that everything now takes an afternoon.

Project evolution already named what that version is: a skeleton with the details left out. The distance between it and something you would put in front of a customer is where the promises go wrong.

Say what is missing

Show the rough version, then name what it does not do yet. No validation, one hard-coded member, nothing stored between refreshes. One sentence, and it buys the only thing you needed from that meeting: agreement about what everybody just looked at.

Leave it out and the sentence still gets said. Later, by somebody asking why the feature they signed off on falls over on an empty list, and you will be explaining the same detail from a worse position.

The estimate still matters

Writing the code got faster. Deciding what to build did not, and neither did the deploy. Enablement counts where the day actually goes, and typing was never the expensive part of it.

Then there is the reading, which is new work. An agent that finishes in an hour hands you an hour of diff you did not write, and code you did not write is slower to read than your own. Steering makes the same point about running two agents at once: they got faster and you did not. So when you say a date, say it including the part where you check the work, or "done" is going to mean two different things in one room.

One good run is not a velocity

Hand the same request over twice and it does not come back the same twice. The unit on repeating patterns draws that spread and then puts a script around the part that should not be varying at all. Until you have done that, the afternoon that went well is one sample.

Promise the next checkpoint instead of the finish. A skeleton on Friday and a green build on Monday are both things a bad run only costs you a day on. A date that assumed every run lands has nowhere to go the first time one does not.
