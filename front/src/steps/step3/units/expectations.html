The people around you saw what you saw. A working version of something, on screen, an afternoon after somebody asked for it. Some of them did not ask at all: the tools are on their laptop too, and a manager can put a prototype together over lunch. What everybody took away is that everything now takes an afternoon.

Project evolution already named what that version is: a skeleton with the details left out. The distance between it and something you would put in front of a customer is where the promises go wrong.

The tool is not the advantage

Management holds a bigger version of that: the tool bought the team an advantage. Your competitor is on the same models, in the same week, reading the same article about them. Whatever the tooling hands you, it hands them. Change management already showed the factor not arriving. This is the other half, and it holds even where the gain is real. A gain everybody gets is the new floor rather than a lead.

What the tool hands you for free has a ceiling too. A model answers from an average, which is what the context unit established, so an ordinary instruction gets ordinary work back. What is left to be better at is what you know about this domain, this codebase and the people using it. None of that arrived with the tool.

Say what is missing

Show the rough version, then name what it does not do yet. No validation, one hard-coded member, nothing stored between refreshes. One sentence, and it buys the only thing you needed from that meeting: agreement about what everybody just looked at. When the prototype is theirs rather than yours, it is the same sentence and it is still yours to say.

Leave it out and the sentence still gets said. Later, by somebody asking why the feature they signed off on falls over on an empty list, and you will be explaining the same detail from a worse position.

The detail nobody specified

An agent implements the request it was given, and the request was shallow. Ask for book returns and that is what comes back, handled, tested, along the path you described. The time then goes on the cases nobody had in mind when that request was written, and nobody includes you. Some of them do not exist until the thing is half built.

From the outside that looks like work which finished on Thursday and then went on for three weeks anyway. Naming the thing you want gets a sharper first draft and it does not get the detail nobody knew about yet. So the burden moved rather than lifted. It sits with the people who can find that detail, and finding it takes room in the week, not a date at the end of it.

The estimate still matters

Writing the code got faster. Deciding what to build did not, and neither did the deploy. Step 2's unit on what it asks of you counts where the day actually goes, and typing was never the expensive part of it.

Then there is the reading, which is new work. An agent that finishes in an hour hands you an hour of diff you did not write, and code you did not write is slower to read than your own. Steering makes the same point about running two agents at once: they got faster and you did not. So when you give a date, give one with the checking inside it, or "done" is going to mean two different things in one room.

One good run is not a velocity

Hand the same request over twice and it does not come back the same twice. The unit on repeating patterns draws that spread and then puts a script around the part that should not be varying at all. Until you have done that, the afternoon that went well is one sample.

You used to correct a number like that by instinct, and that correction is gone. You estimated from years of having done the work, and your manager read the quality off knowing who was on the team; both are readings of a job that changed shape underneath them. Everybody is re-calibrating at once, so the honest promise is the next checkpoint rather than the finish. A skeleton on Thursday, a green build on Monday. A date that assumed every run lands has nowhere to go the first time one does not.
